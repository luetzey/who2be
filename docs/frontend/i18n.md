# Internationalisierung (i18n)

Die Web-UI ist mit [`react-i18next`](https://react.i18next.com/) zweisprachig
(Deutsch + Englisch). Deutsch ist die gewachsene Default- und Fallback-Sprache,
Englisch die Zweitsprache.

## Architektur

- **Init:** `src/i18n/index.ts` initialisiert die i18next-Singleton-Instanz
  (Sprachdetektor + `initReactI18next`). Gebundlet via `import './i18n'` in
  `src/main.tsx`, bevor die App mountet. Tests fixieren die Sprache in
  `src/test/setup.ts` auf `de`.
- **Locale-Dateien:** `src/i18n/locales/de.json` und `en.json`. Die
  Top-Level-Keys sind die **Namespaces** — ein Namespace pro Feature plus die
  geteilten `common`, `layout`, `data`, `version`. `i18next.ns` wird aus den
  Keys von `de.json` abgeleitet; ein neuer Namespace berührt also nur die JSONs.
- **Default-Namespace:** `common`. Cross-Namespace-Zugriff via Präfix:
  `t('common:actions.save')`.

## Verwendung

```tsx
import { useTranslation } from 'react-i18next'

function MyPage() {
  const { t } = useTranslation('personas') // Feature-Namespace
  return <h1>{t('list.title')}</h1>         // + t('common:actions.save')
}
```

- Nicht-Komponenten-Helfer (`.ts`) bekommen entweder `t` durchgereicht oder
  importieren die Singleton-Instanz: `import i18n from '@/i18n'` →
  `i18n.t('ns:key')`. Klassen-Komponenten (z. B. `RouteErrorBoundary`) nutzen
  ebenfalls die Singleton-Instanz.
- Interpolation: `t('key', { name })` mit `{{name}}` im JSON. Pluralisierung
  über i18next-Plural-Suffixe (`key_one` / `key_other`).
- **Geteilte Begriffe** (Aktionen, Feld-Labels, Status, Lade-/Fehlertexte)
  liegen im `common`-Namespace — nicht pro Feature duplizieren.

## Sprachwahl & Persistenz

Zwei Ebenen, bewusst gewählt als der einfachste konsistente Weg ohne
Backend-Migration:

1. **Geräte-Cache (localStorage):** Der
   `i18next-browser-languagedetector` liest/schreibt die Wahl unter
   `who2be.locale` (`LOCALE_STORAGE_KEY`). Erkennungsreihenfolge:
   `localStorage → navigator → htmlTag`.
2. **Geräteübergreifend (Supabase `user_metadata.preferred_locale`):**
   `useLocale().setLocale(loc)` schreibt die Präferenz best-effort via
   `supabase.auth.updateUser({ data: { preferred_locale } })`. Beim Login wendet
   `useApplyStoredLocale()` (montiert in `AppLayout`) diesen Wert an, sodass die
   Sprache dem User auf ein neues Gerät folgt, auf dem der localStorage-Cache
   noch leer ist.

**Vorrang-Regel:** Der gespeicherte Wert ist ein *Startwert*, keine laufende
Quelle der Wahrheit. `setLocale` markiert die Wahl über
`markExplicitLocaleChoice()`; `shouldApplyStoredLocale(userId)` (beides in
`src/i18n/index.ts`) entscheidet dann, ob `useApplyStoredLocale` überhaupt
eingreifen darf — bei einer eigenen Wahl im laufenden Tab nicht mehr, bei einem
**User-Wechsel** dagegen schon. Ohne diesen Vorrang kippt die Sprache zurück:

- Der Session-Bootstrap ist asynchron. Wer den Umschalter im Header bedient,
  bevor `session.user` eintrifft, würde sonst vom gespeicherten Altwert
  überfahren.
- `supabase.auth.updateUser` behält den bestehenden `access_token` bei (es setzt
  nur `session.user`), während `SessionProvider.apply()` genau auf diesen Token
  dedupliziert. Das `USER_UPDATED`-Event wird also verworfen und der
  Session-State im React-Baum trägt weiter die alte `preferred_locale`.

Beide Pfade sind in `src/i18n/useApplyStoredLocale.test.tsx` als
Regressionstests festgenagelt. Der Zustand liegt bewusst im Modul und nicht in
einem Hook-Ref (`AppLayout` wird bei Logout/Login neu gemountet) und nicht in
localStorage (der Sprachdetektor cached dort schon beim Init, ein Cache-Eintrag
belegt also keine bewusste Entscheidung).

Der Umschalter ist als `LanguageSwitcher` (`@/components/ui/language-switcher`,
Dropdown-Primitive) in der `AppShell`-Kopfzeile sichtbar und zusätzlich als
`Select` in den Konto-Einstellungen.

## Content-Sprache (ADR-0045: „ein Element, eine Sprache")

Content-Sprache ist von der UI-String-Sprache getrennt, hängt aber an zwei
Stellen mit ihr zusammen:

- **Workspace-Anlage:** Das `content_locale`-Feld im Workspace-Formular
  (`OrgSettingsPage`) ist aus `useLocale()` vorbelegt; der automatisch
  angelegte persönliche Workspace leitet die Sprache serverseitig aus
  `user_metadata.preferred_locale` ab (Fallback `de`).
- **Elemente:** Jedes Element (Persona/Playbook/Resource/Tool/System-Prompt)
  trägt genau eine Sprache (`locale`), Default = Workspace-Sprache,
  beim Anlegen per Single-Select änderbar; sichtbar als `LocaleBadge`
  (`@/components/data`), filterbar über die Listen-Filterleiste
  (`?locale=`-Filter). Details: `docs/adr/0045-ein-element-eine-sprache.md`.

Der API-Client (`src/api/client.ts`) sendet die aktive UI-Sprache weiterhin
als `Accept-Language`-Header mit (`i18n.resolvedLanguage`); für die
Content-Auswahl ist er seit ADR-0045 ohne Bedeutung.

## Neue Strings hinzufügen

1. Key im passenden Namespace in **beiden** Locale-Dateien anlegen (gleiche
   Key-Struktur in `de.json` und `en.json`).
2. Im Code via `t('key')` referenzieren.
3. Tests laufen auf Deutsch — assertierte Strings müssen exakt dem `de`-Wert
   entsprechen.

### Auflösungszeitpunkt: immer lazy

`i18n.t(...)` **niemals** auf Modul-Ebene auswerten. Ein Modul wird einmal
geladen (bei Route-Chunks: irgendwann während der Session) und friert den Text
auf die dann aktive Sprache ein — ein späterer Sprachwechsel geht daran vorbei.
Das betraf u.a. die zod-Schemata; ein Test hatte den Effekt sogar als erwartetes
Verhalten festgeschrieben (englische Meldung in einer deutschen Suite).

- **Komponenten:** `useTranslation(ns)` und `t('key')` im Render.
- **zod-Schemata:** die Lazy-Form von Zod 4 —
  `z.string().min(1, { error: () => i18n.t('common:validation.nameRequired') })`.
  Die Message wird dann zur Validierungszeit aufgelöst.
- **Nicht-Komponenten** (Hooks, `lib/`, Klassen-Komponenten): Singleton-Instanz
  `import i18n from '@/i18n'` → `i18n.t('ns:key')` **innerhalb** der Funktion,
  nicht in einer Modul-Konstanten.

### Was NICHT übersetzt wird

- **Persistierte Inhalte.** Das `label` einer Placeholder-Pill im
  System-Prompt-Editor ist eine BlockNote-Prop und wird ins Dokument
  geschrieben. Es gehört damit zur Sprache des Elements (ADR-0045), nicht zur
  UI-Sprache, und bleibt ein stabiles Literal — sonst trägt derselbe Prompt je
  nach Bediener gemischtsprachige Pills. Übersetzt wird die *Anzeige* im Picker
  (`labelKey`/`descriptionKey`), nicht der gespeicherte Wert. Dasselbe gilt für
  Entity-Namen-Defaults (z.B. `createAgent({ name: 'Neuer Agent' })`).
- **Entwickler-Ausgaben.** `console.error`-Texte, Boot-Fehler in `main.tsx` und
  `config.ts` laufen vor bzw. neben der UI und bleiben deutsch.
- **Server-Fehlertexte.** `apps/api` liefert `detail` fest auf Deutsch und liest
  `Accept-Language` nicht; der Client zeigt den Text wörtlich an. Offen als
  eigene Architektur-Entscheidung — siehe Issue #402.
- **`src/app/catalog/**`.** DEV-only Showcase, nicht Teil des Produktions-Bundles.
