## FAIL-Ursachen

### FT-VER-05: Reset (active→draft) — Rollen-Diskrepanz

**Symptom:** `POST /versions/{v}/transition {to:"draft"}` mit Editor-Token auf einer aktiven Version → **403** `"Diese Aktion erfordert mindestens die Rolle 'admin'."`. Mit Admin-Token → 200.

**Code-Fundstelle:** `apps/api/src/who2be_api/services/version_status.py`, Funktion `required_role_for_transition`:

```python
if (
    to_status in (VersionStatus.active, VersionStatus.inactive)
    or from_status == VersionStatus.active   # ← schließt active→draft ein
):
    return WorkspaceRole.admin
```

Der Kommentar im Code sagt explizit: *„Reset-auf-Draft (`active → draft`, Track A) — Admin-only"*.

**Spec-Fundstelle:** `CLAUDE.md` Status-Maschine-Sektion: `active→draft (Reset, editor)`. Testplan FT-VER-05: Rolle `editor`.

**Empfehlung:** Entweder `required_role_for_transition` so anpassen, dass `active → draft` mit `editor` erlaubt ist (spec-konform), oder CLAUDE.md + Testplan aktualisieren um das Admin-Requirement zu dokumentieren (bewusste Entscheidung).

## Beobachtungen (außerhalb Scope)

1. **Promote-Validierung feuert bereits bei draft→review** (nicht erst bei review→active): `POST /transition {to:"review"}` auf leerer Resource gibt 409 `promote-validation-failed` mit `missing:["description","body"]`. Dies ist strenger als der Testplan beschreibt (der sagt „Promote (Review→Active): 409 bei fehlenden Feldern"). Könnte beabsichtigt sein (kein Review leerer Drafts), sollte aber im Testplan dokumentiert werden.

2. **Playbook/SP `content.body` ist ein String (stringifiziertes JSON)**: Das Schema für Playbooks und System-Prompt-Templates unterscheidet sich von Resources — `body` ist ein `str` (BlockNote-JSON-String), nicht ein verschachteltes Objekt. Resources hingegen haben `content.blocks` als Array. Diese Asymmetrie kann zu Verwirrung bei API-Consumers führen.

3. **Sub-Resource Schema-Key**: `PUT /sub_resources` erwartet `{"links":[{"child_id":…}]}` — `child_id` (nicht `child_resource_id`) und ein `links`-Wrapper. Der Testplan-Hinweis `block_id, position, scope, embedding_mode` entspricht der alten `ResourceLinkItem`-Syntax; die korrekte ist `SubResourceLinkItem` mit `child_id`.

4. **Resource-Link block_id + link_scope='resource'**: Wenn `link_scope='resource'` gesetzt ist, darf kein `block_id` mitgegeben werden (→ 422 `"link_scope='resource' darf kein block_id setzen"`). Nur `link_scope='block'` erlaubt `block_id`, und dann muss der Block ein Heading sein (`"Nur Heading-Blöcke sind als Anker erlaubt"`).
