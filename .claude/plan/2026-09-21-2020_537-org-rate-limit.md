# #537 — MCP-Minutenlimit pro Organisation statt pro Token (Option A)

Issue: luetzey/who2be#537 (K2 von #535) · Branch: `wt/i537-org-rate-limit`
Owner-Entscheidung: **Option A** — Org-Ceiling = `mcp_rate_per_min` (derselbe
Wert wie das Token-Ceiling, Free 30 / Pro 240), effektiv gilt das Minimum.
Kein neues Entitlement-Feld, keine Migration, keine Aenderung an `plans.md`.

## Ist-Zustand (nachgemessen 2026-09-21, main @ 69bfeda)

- `mcp_limit_service.py:95` — `token_rate_limiter.allow(rate_limit_key(request), rate)`.
  `rate_limit_key()` (`core/rate_limit.py:40`) hasht den Bearer-Token ⇒ **ein
  Bucket pro Token**, N Tokens = N × Rate.
- `_resolve_org_id()` (`mcp_limit_service.py:59`) laeuft bereits vor dem
  Rate-Check ⇒ die Org ist bekannt, **kein zusaetzlicher Query**.
- `TokenRateLimiterPort.peek()` existiert (In-Memory + Redis) und ist genau
  die nicht-konsumierende Pruefung, die der Doppel-Bucket braucht.

## Umsetzung

`McpLimitService.enforce()`, Schritt 1:

1. `token_key = rate_limit_key(request)`, `org_key = f"org:{org_id}"`.
2. **Erst beide `peek()`** — lehnt einer ab, wird 429 geworfen, **ohne** dass
   eines der beiden Fenster konsumiert wurde (und ohne Kontingentverbrauch,
   weil der Rate-Check vor `increment_if_allowed` liegt).
3. **Dann beide `allow()`** (beide werden ausgewertet, kein Short-Circuit, damit
   die Buckets symmetrisch bleiben). Schlaegt unter Nebenlauf doch einer fehl,
   ebenfalls 429.
4. Beide Ablehnungen nutzen **dieselbe** Fehlerstelle: `reason="mcp_rate_limited"`,
   `params={"limit": rate}`, `Retry-After: 60`, unveraenderter `detail`-Text
   (Locale-Keys `de/en.json`, `apps/web/src/api/client.test.ts` und die
   Smoke-Checklisten haengen daran — nicht anfassen).

Unveraendert: `is_cloud()`-Wache als erster Ausstieg (On-Prem/OSS), JWT-Pfad,
`rate is None` ⇒ beide Buckets lassen durch (`allow`/`peek` kurzschliessen bei
`None`/`<= 0`).

## Tests (`apps/api/tests/test_mcp_limit_service.py`, `test_token_rate_limiter.py`)

- Zwei Tokens derselben Org, jedes unter seinem Ceiling, zusammen darueber ⇒
  429, `reason="mcp_rate_limited"`, `Retry-After: 60`.
- Zwei Tokens **verschiedener** Orgs beeinflussen sich nicht (Trennung belegt).
- Abgewiesener Request verbraucht **weder** Monatskontingent **noch**
  Token-Fenster (Token-Bucket danach noch frei ⇒ `peek` beweist es).
- `mcp_rate_per_min is None` ⇒ beide Buckets lassen durch; On-Prem unveraendert.
- Redis-Pfad: `RedisTokenRateLimiter` mit `peek`/`allow` gegen zwei Keys
  (Fake-`limits`-Storage, kein laufendes Redis noetig).
