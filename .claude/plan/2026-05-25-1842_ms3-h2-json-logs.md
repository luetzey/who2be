# Plan: MS-3 H2 — Strukturierte JSON-Logs (API + MCP)

## Context

Stand: H1 (Rate-Limiting) ist gemergt (PR #9). H2 ist die naechste MS-3-Hardening-Task in Roadmap-Reihenfolge, disjunkt zu H3 (Security-Review). Ziel laut `2026-05-24_who2be-mvp-roadmap.md`:

> API + MCP loggen JSON-Zeilen mit `request_id`, `owner_id`, `path`, `status`, `duration_ms`. `structlog` oder `logging.config.dictConfig`-Json — eine Wahl, im ADR-0007 festgehalten.

Heute loggen API und MCP fragmentarisch mit stdlib `logging.getLogger(__name__)` (`apps/api/src/who2be_api/core/db.py:18`, `core/security.py:22`, `apps/mcp/src/who2be_mcp/client.py:17`) — Default-Formatter, keine zentrale Konfiguration, keine Request-Korrelation. Es existiert weder ein `core/logging.py` noch eine Request-ID-Middleware. ADR-Reihe ist bis 0006 belegt; 0007 ist frei.

## Approach

**Library:** `structlog>=24.1` mit den eingebauten `contextvars`-Bindings. Begruendung:
- Native Context-Binding ueber `contextvars` (asyncio-safe, anders als `logging.LoggerAdapter`)
- Composable Processor-Pipeline → `JSONRenderer` fuer Prod, optional `ConsoleRenderer` fuer lokal
- mypy-strict-freundlich (typed Stubs, `BoundLogger.info(event: str, **kwargs)`)
- Bestehende `logging.getLogger`-Calls bleiben funktional: structlog kann ueber `ProcessorFormatter` die stdlib-Records mitformatieren, sodass `db.py`/`security.py`/`client.py` ohne Refactor JSON ausgeben.

**Korrelations-Felder:**
- `request_id` — UUID4, von Middleware generiert (oder aus `X-Request-ID`-Header uebernommen), in `contextvars.ContextVar` gesetzt und als Response-Header `X-Request-ID` zurueckgegeben.
- `owner_id` — von `get_current_user` (`core/security.py:86-108`) gesetzt; minimal-invasiv: Dependency setzt die Context-Var selbst (keine Wrapper-Dependency, kein Router-Refactor noetig).
- `path`, `status`, `duration_ms` — von einer schmalen Access-Log-Middleware nach `await call_next(request)` emittiert.

**MCP:** Kein HTTP-Request-Konzept, also pro Tool-Aufruf ein contextvars-Reset + ein `request_id = uuid4()`. Das geht als duenner Decorator (`@with_tool_log`) **on top** der `@mcp.tool`-Decoratoren — die vier bestehenden Tools werden jeweils einmal damit gewrappt.

**Config:** `LOG_FORMAT={"json"|"console"}` Setting (Default `json`), damit lokal `uvicorn --reload` lesbar bleibt.

## File-by-file Changes

### 1. `apps/api/pyproject.toml` — Dependency
Ergaenze in `dependencies`:

```toml

```

### 2. `apps/mcp/pyproject.toml` — gleiche Dependency
`"structlog>=24.1"` ebenfalls aufnehmen (uv-Workspace teilt nicht automatisch, weil API/MCP separat installiert sein muessen).

### 3. `apps/api/src/who2be_api/core/config.py` — Log-Setting
Neues Feld in `Settings` (analog `rate_limit_write:50`):

```python
log_format: Literal["json", "console"] = "json"
```

### 4. `apps/api/src/who2be_api/core/logging.py` — NEU
- `request_id_var: ContextVar[str | None]`, `owner_id_var: ContextVar[str | None]` als Modul-Singletons.
- `configure_logging(format: Literal["json","console"]) -> None`: konfiguriert structlog mit Processor-Chain (`merge_contextvars`, `add_log_level`, `TimeStamper(fmt="iso")`, dann `JSONRenderer()` oder `ConsoleRenderer()`); ruft `logging.basicConfig(handlers=[StreamHandler], level=INFO)` + setzt `ProcessorFormatter` als Root-Handler-Formatter (damit stdlib-Logger den gleichen Output bekommen).
- `get_logger(name: str | None = None) -> structlog.stdlib.BoundLogger`.
- Idempotent: zweiter Aufruf ist no-op (Flag `_configured`).

### 5. `apps/api/src/who2be_api/core/middleware.py` — NEU
Zwei kleine ASGI-Middleware-Klassen (kein `BaseHTTPMiddleware` — der konsumiert den Request-Body unnoetig):

- **`RequestIDMiddleware`**: liest `X-Request-ID` aus dem Header, sonst `uuid4().hex`; setzt `request_id_var`; setzt im Response-Start den Header `X-Request-ID`.
- **`AccessLogMiddleware`**: misst `time.perf_counter()`-Delta um den `app`-Call; loggt am Ende `event="http_request"`, `path=request.url.path`, `method`, `status`, `duration_ms`. `owner_id` kommt automatisch aus der ContextVar.

### 6. `apps/api/src/who2be_api/main.py` — Wiring
- Vor `app = FastAPI(...)`: `configure_logging(get_settings().log_format)`.
- Nach den existierenden `add_middleware`-Calls: `app.add_middleware(AccessLogMiddleware)`, dann `app.add_middleware(RequestIDMiddleware)`. Reihenfolge wichtig (Starlette stacked LIFO): RequestID muss aussen liegen, damit AccessLog die ID schon sieht; CORS und SlowAPI bleiben innen-aussen wie bisher.

### 7. `apps/api/src/who2be_api/core/security.py` — owner_id-Context setzen
In `get_current_user` (Z. 86–108), unmittelbar vor jedem `return owner_id` / `return verify_supabase_jwt(token)`:

```python
owner_id_var.set(str(owner_id))
return owner_id
```

(3 Stellen: pre-401-return ueberspringen, JWT-Pfad, Token-Pfad.) Minimal-invasiv, kein Router-Refactor.

### 8. `apps/mcp/src/who2be_mcp/core_logging.py` — NEU
- Eigenes Modul (nicht aus API importieren — bewusste Trennung, ADR-0005).
- Identische `configure_logging`-Funktion (kopiert, ohne owner_id — MCP kennt keinen).
- Decorator `with_tool_log(tool_name: str)`: setzt `request_id_var`, misst Dauer, loggt `event="mcp_tool_call"`, `tool=tool_name`, `duration_ms`, `error` (falls Exception). Async- und Sync-Variante unterscheidet sich nicht durch `inspect.iscoroutinefunction`.

### 9. `apps/mcp/src/who2be_mcp/server.py` — Wiring
- In `main()` vor `mcp.run()`: `configure_logging(get_settings().log_format)`.
- Jedes `@mcp.tool` zusaetzlich mit `@with_tool_log("name")` dekorieren (4 Stellen: `ping`, `get_persona`, `list_playbooks`, `fetch_playbook`).
- `apps/mcp/src/who2be_mcp/config.py` braucht ein `log_format`-Feld analog zur API.

### 10. `apps/api/tests/test_logging.py` — NEU
- Test 1: `test_request_id_header_round_trip` — ohne Client-Header bekommt die Response einen neuen `X-Request-ID`; mit Client-Header wird der propagiert.
- Test 2: `test_access_log_emits_required_fields` — `caplog`-basiert, capture aller Records, filter auf `event=="http_request"`, assert dass das gerenderte Record-Dict (`record.msg` ist nach structlog stdlib-Integration ein dict-aehnliches Objekt; alternativ `caplog.records[0].args` oder via `structlog.testing.capture_logs`) folgende Keys hat: `request_id`, `owner_id`, `path`, `status`, `duration_ms`. Anon-Request (kein Auth) → `owner_id` ist `None`/fehlt; authed Request → vorhanden.
- Test 3: `test_log_format_console_for_dev` — `monkeypatch` `LOG_FORMAT=console`, reconfigure, assert dass Output kein valides JSON ist (= ConsoleRenderer aktiv).

Test-Pattern: `structlog.testing.capture_logs()` als Context-Manager — sauberer als `caplog`, kein JSON-Re-Parse noetig.

### 11. `apps/mcp/tests/test_tool_logging.py` — NEU
- `with capture_logs() as logs:` und `await ping()` → assert `logs[-1]` enthaelt `tool="ping"`, `request_id`, `duration_ms`.
- Fehlerfall: `with_tool_log` muss bei Exception trotzdem `error`-Feld setzen und Exception re-raisen.

### 12. `docs/adr/0007-strukturierte-logs.md` — NEU
Format analog `0006-auth-jwt-und-api-token.md`:
- Status: Akzeptiert · Datum: 2026-05-25 · Kontext: Who2Be MVP (PROJ-19)
- **Optionen:**
  - A — `structlog` mit `ProcessorFormatter` ueber stdlib
  - B — `python-json-logger` + `logging.config.dictConfig`
  - C — Eigener `logging.Formatter` mit JSON-Dump
- **Entscheidung:** A. Begruendung: context-binding ueber `contextvars` ohne LoggerAdapter-Boilerplate; bestehende `logging.getLogger`-Calls werden via ProcessorFormatter mit-formatiert; async-safe; `JSONRenderer` ist umschaltbar gegen `ConsoleRenderer` fuer DX.
- **Konsequenzen:** Eine zusaetzliche Dependency in API und MCP; Log-Aggregator (Loki/CloudWatch) muss JSON parsen koennen; `request_id`-Header standardisiert (auch fuer kuenftiges Tracing).

## Verifikation

Lokal in dieser Reihenfolge:

1. **Install**: `uv sync` — `structlog` in `uv.lock`.
2. **Lint+Type**: `uv run ruff check . && uv run ruff format --check . && uv run mypy .` — gruen.
3. **Unit-Smoke**: `uv run pytest -q apps/api/tests/test_logging.py apps/mcp/tests/test_tool_logging.py` — gruen.
4. **Vollsuite**: `uv run pytest -q` — keine Regression in den 79 bestehenden Tests, insbesondere `test_rate_limit.py` und `test_db.py` (die nutzen `caplog`).
5. **Manueller API-Smoke**: `uv run uvicorn who2be_api.main:app --reload` → `curl -i http://localhost:8000/v1/health`. Erwartung:
   - Response-Header `X-Request-ID: <hex>` vorhanden.
   - Stdout zeigt eine JSON-Zeile mit `event="http_request"`, `path="/v1/health"`, `status=200`, `duration_ms=<float>`, `request_id=<hex>`.
6. **Custom-Header-Test**: `curl -H "X-Request-ID: trace-abc-123" http://localhost:8000/v1/health` → der gleiche Wert taucht in Header und Log auf.
7. **MCP-Smoke**: `uv run python -m who2be_mcp.server` lokal starten, ueber MCP-Inspector `ping` aufrufen → JSON-Logzeile `event="mcp_tool_call"`, `tool="ping"`, `duration_ms=<float>`.
8. **DX-Check**: `LOG_FORMAT=console uv run uvicorn ...` → lesbarer Console-Output (key=value), kein JSON.

## Out of Scope (bewusst)

- Distributed Tracing / OpenTelemetry (Folge-Plan, frueheste Stelle MS-3+ oder Post-MVP).
- Log-Aggregation (Loki / CloudWatch / etc.) — Setup gehoert zu MS-2 Hetzner-Deploy.
- Sensible-Daten-Redaction (Token, Email) — wir loggen keine Bodies, nur Metadaten; daher kein Filter noetig im H2-Scope.
- Web-Frontend-Logging.
- `LogLevel`-Setting (Default INFO reicht; Debug-Schalter folgt bei Bedarf).
- Persistenter `request_id`-Propagation API → MCP-Client-Calls (Cross-Service-Trace) — eigene Spaeter-Task.
