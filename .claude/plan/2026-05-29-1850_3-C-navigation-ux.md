## Umsetzung

### 1. WorkspaceSwitcher

- **Neu** `apps/web/src/components/layout/WorkspaceSwitcher.tsx`:
  - `DropdownMenu` (shadcn-Primitive) als Sidebar-Header.
  - Trigger: aktueller Workspace-Name + `ChevronsUpDown`-Icon, role
    `combobox` (a11y).
  - Content: pro Organization eine `DropdownMenuLabel` (Org-Name +
    `kind`-Badge subtle) gefolgt von `DropdownMenuItem`-Liste mit den
    Workspaces dieser Org. Check-Icon links neben dem aktiven Workspace.
  - Separator + `DropdownMenuItem` "Workspace anlegen" → `<Link to="/settings/orgs">`
    (Route existiert heute nicht — bleibt graceful, wird in Folge-Track
    geliefert).
- Datenquelle: `useSession().me?.organizations ?? []`. Wenn `me === null`
  oder leer → Component rendert nichts (defensiv; AppShell wird sowieso
  hinter `RequireAuth` gemounted).
- Wechsel: `navigate(\`/w/${ws.id}/dashboard\`)` +
  `localStorage.setItem('lastWorkspaceId', ws.id)`. Wenn Click auf den
  bereits aktiven WS → no-op (Dropdown schliesst nur).
- **AppShell** (`apps/web/src/components/layout/AppShell.tsx`):
  WorkspaceSwitcher direkt oberhalb der Nav-Liste mounten, der bisherige
  "Who2Be"-Brand-Text bleibt darueber (kleiner Eyebrow).

### 2. Status-Action-Bar immer sichtbar

- Drei `StatusActionBar`-Komponenten (`features/{personas,playbooks,resources}/components/StatusActionBar.tsx`):
  - Neuer Button "Reaktivieren als Draft" bei `status='inactive'`
    (`variant="outline"`). Klick triggert `transition(..., 'draft', ...)`.
  - Bedingung: `showReactivate = status === 'inactive' && canTransition(status, 'draft')`.
  - `if (!showSubmit && !showPromote && !showReject && !showReactivate)` → return null.
- Drei `features/{personas,playbooks,resources}/lib/status.ts`:
  - `ALLOWED_TRANSITIONS.inactive = ['draft']` (war `[]`).
- Detail-Pages — `actionableVersion` erweitern:
  - Heute: `draftVersion ?? reviewVersion`. Bleibt Vorrang.
  - Neu: Fallback auf die Version, die `current_version` ist UND
    `status='inactive'` hat. Damit zeigt die Bar fuer reine inactive-
    Bestaende den Reactivate-Button.
  - Active-only: kein Fallback → Bar bleibt null (kein leerer Toolbar).
- Tests: bestehende `StatusActionBar.test.tsx` in allen drei Features
  ergaenzen — neue Erwartung fuer `inactive` (Button erscheint + Transition-
  Endpoint wird gerufen). Keine Snapshot-Tests; Variante "4 Status-
  Zustaende" wird ueber 4 `it()`-Bloecke abgedeckt.

### 3. Backlinks anzeigen

- **PlaybookDetailPage** — neuer Block "Verwendet in" (Card + DataList):
  - Daten via neuem Hook `usePlaybookUsages(id)` (analog
    `usePlaybookResourceLinks`): `api.getPlaybookUsages(id)`.
  - Empty: `<EmptyState>` Microcopy "Noch in keiner Persona verwendet —
    verknuepfe dieses Playbook im Persona-Editor, um es einer Persona
    zuzuweisen."
  - Loading/Error via `DataView`. 404 → wir behandeln das als
    `empty` (Track A noch nicht gemerged → 404 ist erwartbar).
- **ResourceDetailPage** — neuer Block "Verlinkt in":
  - Hook `useResourceUsages(id)`: `api.getResourceUsages(id)`.
  - Pro Eintrag: Playbook-Name + Block-Count-Badge.
  - Empty-Microcopy: "Noch in keinem Playbook verwendet — verlinke einen
    Heading-Block in einem Playbook, um diese Resource sichtbar zu
    machen."
- 404-Handling: zentral im jeweiligen Hook — wenn `error?.status === 404`
  ist, setzen wir `error=null, usages=[]` und zeigen den EmptyState.
- **Hooks** kommen unter `apps/web/src/hooks/` (cross-feature: `Resource`-
  oder `Playbook`-Backlink wird in beiden Features konsumiert; Plazierung
  unter `hooks/` umgeht den Cross-Feature-Lint-Gate).

### 4. API-Client + Types

- `apps/web/src/api/types.ts`:
  - `export interface PlaybookUsage { persona_id: string; persona_name: string }`
  - `export interface ResourceUsage { playbook_id: string; playbook_name: string; block_count: number }`
  - `export type PlaybookType = 'prompt' | 'instructions' | 'snippet' | 'workflow' | 'checklist' | 'faq'`
  - `ResourceLink.available_in?: 'active' | 'draft' | null` ergaenzen (das
    Plan-Doc bezeichnet das Feld als `LinkedBlock.available_in`; in unserem
    Repo heisst die Schnittstelle `ResourceLink`. Bestehendes
    `available: boolean` bleibt — Backend liefert beides bis Track A
    explizit migriert).
- `apps/web/src/api/client.ts`:
  - `getPlaybookUsages(id) → /v1/workspaces/{ws}/playbooks/{id}/usages`
  - `getResourceUsages(id) → /v1/workspaces/{ws}/resources/{id}/usages`
  - `getPlaybookTags()    → /v1/workspaces/{ws}/playbooks/tags`
  - Methoden in `Api`-Interface erweitern.
