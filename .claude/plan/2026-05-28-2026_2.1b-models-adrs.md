## Architektur-Entscheidungen

- **`VersionStatus` als `StrEnum`** (statt `Literal[...]`): Single-Source
  fuer Wert + Iterierbarkeit. Repos/Services brauchen `for status in
  VersionStatus`, Service-Layer braucht ein Lookup `ALLOWED_TRANSITIONS:
  Mapping[VersionStatus, frozenset[VersionStatus]]`. Mit
  `Literal[...]` muesste man die Werte doppelt pflegen. Pydantic
  serialisiert `StrEnum` transparent als String (validiert auch
  String-Inputs vom JSON-Body).
- **Transition-Tabelle in `status.py`** (nicht im Service), damit MCP /
  Web denselben Vertrag sehen. Definition:
  - `draft → {review, inactive}`
  - `review → {draft, active, inactive}`
  - `active → {inactive}`
  - `inactive → {}` (terminal — passt zum Migration-Backfill, in dem alle
    nicht-`current_version`-Eintraege auf `inactive` gehen und dort
    bleiben)
  - Hilfs-Funktion `is_allowed_transition(from_, to)` plus Konstante
    `ALLOWED_TRANSITIONS` (frozen).
- **`StatusHistoryEntry` ist read-only**: spiegelt eine `status_history`-
  Zeile inkl. `id`. `entity_type` als `Literal['persona','playbook','resource']`
  — identisch zum DB-CHECK in `0012_status_history.sql`. Resource ist
  schon enthalten, weil DB-Spalte ihn akzeptiert (Plan §2.1.A) — billig,
  spaeter Migrationen zu sparen.
- **`DashboardResponse` ist read-only Vertrag**: drei in sich
  abgeschlossene Sub-Modelle (`DashboardKpis`, `EntityStatusDistribution`,
  `DashboardStatusDistribution`), keine Service-Logik. `activity`-Liste
  ist `list[StatusHistoryEntry]` — wiederverwendetes Modell, kein neuer
  Activity-Event-Typ. Plan §2.1.E nennt nur Status-Wechsel-Events; eine
  generische "Event"-Hierarchie waere YAGNI.
- **`current_status` + `has_pending_draft` mit Defaults** auf
  `PersonaRead`/`PlaybookRead`: `current_status` default `VersionStatus.inactive`,
  `has_pending_draft` default `False`. Damit bleiben existierende API-
  Unit-Tests (`test_personas.py`, `test_playbooks.py` etc.), die diese
  Felder nicht uebergeben, valide. Repo-Code in 2.1b-1 setzt die Felder
  scharf; bis dahin sehen Clients `inactive`/`False` als sicheren Default.
- **`status` auf `PersonaVersionRead`/`PlaybookVersionRead` mit Default**
  `VersionStatus.inactive`: deckt die Migration-Default-Linie aus
  `0011_status_on_versions.sql` (`DEFAULT 'inactive'`). Existierende
  Antworten der bestehenden List-Versions-Endpoints bleiben damit
  schema-konform — sie liefern bisher kein `status` und werden in 2.1b-1
  umgebogen.
- **Pydantic `max_length` / `extra="forbid"`-Linie weiterfuehren**
  (F-01): `StatusHistoryEntry` setzt `note: str | None = Field(default=None,
  max_length=2_000)`. Keine `extra="forbid"` bei Read-Models, konsistent
  mit den existierenden `…Read`-Klassen (die nutzen nur `from_attributes=True`).

ADRs (neu unter `docs/adr/`):

- `0019-tenant-org-workspace.md`
  - **Status:** Akzeptiert, **Datum:** 2026-05-28, **Kontext:** Phase 2.1a.
  - Kontext: Single-Owner-Tenancy reichte fuer MVP, vollwertige App
    braucht Org+Workspace-Hierarchie + Personal-Org-Auto-Create fuer
    Bestandsdaten.
  - Optionen: A) Direkt `User → Workspace` (flach, kein Org-Konstrukt) ·
    B) `User → org_member → Organization → Workspace` (gewaehlt) ·
    C) Single-Tenant-Forever (status quo, zukunftsdicht limitiert).
  - Entscheidung: B. Personal-Orgs (`kind='personal'`) werden beim
    ersten Login auto-angelegt und fuer Bestand via Backfill-Migration
    `0013_backfill_tenants.sql` (eine Personal-Org je distinct
    `owner_id`, Default-Workspace "Personal", `workspace_member`-Row
    als `admin`). `workspace_member` wird schon in 2.1a befuellt, in
    2.3 echt benutzt — damit kein Backfill mehr noetig ist.
  - Konsequenzen: Repository-Layer filtert auf `workspace_id`,
    `owner_id` bleibt als Audit-Spalte (`created_by`), Composite-FK in
    `persona_playbook` wird auf `(workspace_id, persona_id)` / `(workspace_id,
    playbook_id)` umgebaut (Defense-in-Depth). Token-Scope pro Workspace.
- `0020-status-pro-version.md`
  - **Status:** Akzeptiert, **Datum:** 2026-05-28, **Kontext:** Phase 2.1b.
  - Kontext: Editing soll Active-Versionen nicht mutieren; Reviewer-Flow
    in 2.3 braucht erkennbare Zwischenzustaende; MCP soll deterministisch
    nur `active` zurueckgeben.
  - Optionen: A) Status auf Aggregat-Zeile (persona.status) ·
    B) Status pro Version + DB-Invariante via Partial Unique Indices
    (gewaehlt) · C) Kein Status, Versionen anonym numerisch.
  - Entscheidung: B. `VersionStatus = {draft, review, active, inactive}`
    auf `persona_version` und `playbook_version`. State-Machine in
    `packages/models/src/who2be_models/status.py`:
    `draft → {review, inactive}`, `review → {draft, active, inactive}`,
    `active → {inactive}`, `inactive` terminal. DB erzwingt "max. 1
    Draft/Review/Active je Entity" via Partial Unique Indices
    (`0011_status_on_versions.sql`). Status-Wechsel bumpt **keine**
    Version; Audit in separater `status_history`-Tabelle
    (`0012_status_history.sql`).
  - Konsequenzen: PUT auf Active-Persona erzeugt neue Draft-Version
    (`current_version + 1`, `status='draft'`); 409 wenn bereits ein
    Draft existiert. MCP-Read-Tools filtern Server-seitig auf
    `status='active'`. Dashboard liest KPIs + Activity aus
    `status_history` + Aggregat ueber `*_version.status`.
