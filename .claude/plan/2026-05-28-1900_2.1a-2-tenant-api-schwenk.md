## Context

Phase 2.1a-1 (Commit `9e35449`) hat das Tenant-Datenmodell als Migrations 0005–0013 eingespielt: `organization`, `org_member`, `workspace`, `workspace_member`, `status_history` plus nullable `workspace_id`-Spalten auf `persona`/`playbook`/`api_token` mit Backfill. Bewusst **noch offen**: der Schema-Lock (`NOT NULL`, Composite-FK-Switch auf `persona_playbook`) und der gesamte API/MCP/Web-Schwenk auf `WorkspaceContext`. Solange das nicht passiert, hat 2.1a-1 kein User-Outcome – Cross-Workspace-Leaks sind nur DB-strukturell vorbereitet, aber nicht in der Anwendung durchgesetzt.

Sub-Task 2.1a-2 schließt diese Lücke und liefert das Parent-Plan-Deliverable `feat/2.1a-tenancy` aus `.claude/plan/2026-05-27-1921_phase-2-vollwertige-app.md` §2.1.I: existierende Features funktionieren wie vorher, aber unter `/v1/workspaces/{workspace_id}/...` bzw. `/w/{workspace_id}/...`, mit DB-erzwungener Workspace-Isolation. Status-Workflow (Transition-Endpoints, Status-UI) und Dashboard kommen in 2.1b — bewusst getrennter PR.

**User-Entscheidungen** (per AskUserQuestion):
- Scope: Backend + MCP + Web komplett in einem Sub-Task.
- URL-Schema: Hard-Cut auf `/v1/workspaces/{workspace_id}/...` (Plan §2.1.C, kein v2-Parallelbetrieb).
- Workspace-Resolution: neuer `GET /v1/me`-Endpoint, Web/MCP lesen daraus den `default_workspace_id`. Kein Workspace-Switcher in dieser Sub-Task (kommt mit 2.1b oder 2.1a-3).

## Datenmodell — Migration 0014

**NEU** `apps/api/src/who2be_api/migrations/0014_finalize_workspace_id.sql` — idempotenter Schema-Lock in dieser Reihenfolge (FK-Constraint-Reihenfolge wichtig):

1. `ALTER TABLE persona ALTER COLUMN workspace_id SET NOT NULL`; analog `playbook`, `api_token`.
2. `ALTER TABLE persona ADD CONSTRAINT persona_workspace_id_id_key UNIQUE (workspace_id, id)`; analog `playbook`, `api_token`. (Voraussetzung für neue Composite-FKs.)
3. `ALTER TABLE persona_playbook ADD COLUMN workspace_id uuid`; Backfill `UPDATE persona_playbook pp SET workspace_id = p.workspace_id FROM persona p WHERE pp.persona_id = p.id`; `SET NOT NULL`.
4. `ALTER TABLE persona_playbook DROP CONSTRAINT persona_playbook_owner_id_persona_id_fkey, DROP CONSTRAINT persona_playbook_owner_id_playbook_id_fkey` (Namen aus 0004 verifizieren — ggf. via `information_schema` Auto-Name).
5. `ALTER TABLE persona_playbook ADD CONSTRAINT ... FOREIGN KEY (workspace_id, persona_id) REFERENCES persona (workspace_id, id) ON DELETE CASCADE`; analog für `playbook`.
6. `owner_id`-Spalten bleiben überall als Audit-Spalte (`created_by`) — Plan §2.1.A "bitter zu droppen, billig zu behalten".

Idempotenz: jede Anweisung mit `IF NOT EXISTS` / `IF EXISTS` bzw. via `DO $$ ... $$` Block über `pg_constraint`-Lookup, damit `apply_migrations` re-runnable bleibt (Pattern aus 0013).

## Backend — Refactor bestehender Code (Pattern)

Drei wiederkehrende Patterns über alle existierenden Touch-Points:

| Layer | Pattern | Repräsentative Pfade |
|---|---|---|
| Router | `OwnerId = Annotated[UUID, Depends(get_current_user)]` → `Ctx = Annotated[WorkspaceContext, Depends(get_current_workspace)]`; Service-Calls erhalten `ctx` statt `owner_id`; eigener Router-Prefix kürzen | `apps/api/src/who2be_api/routers/{personas,playbooks,tokens,persona_playbooks}.py` |
| Service | Erstes Argument `owner_id: UUID` → `ctx: WorkspaceContext`; INSERT-Pfade setzen `workspace_id=ctx.workspace_id, owner_id=ctx.user_id` (audit) | `apps/api/src/who2be_api/services/{persona,playbook,token,persona_playbook}_service.py` |
| Repository | `WHERE p.owner_id = $1` → `WHERE p.workspace_id = $1` in allen `_SELECT_CURRENT`/Delete/Update-Queries; `persona_playbook_repository.set_links` schreibt `workspace_id` in den INSERT (passt zur neuen Composite-FK) | `apps/api/src/who2be_api/repositories/{persona,playbook,token,persona_playbook}_repository.py` |

`PgTokenRepository.fetch_owner_by_hash` muss zusätzlich `workspace_id` aus dem Token-Row zurückgeben (Spalte existiert seit 0010), damit `get_current_workspace` den Mismatch-Check fahren kann.
