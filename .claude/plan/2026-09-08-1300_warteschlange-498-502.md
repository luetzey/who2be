## Paket 1 — #498: CI bricht bei openapi-Drift

### Fertig heißt

Ein PR, der die API-Oberfläche oder ein Schema ändert, ohne
`docs/reference/openapi.json` neu zu generieren, wird in CI rot — mit einer
Fehlermeldung, die das Regenerierungs-Kommando nennt.

### Ist-Zustand (gemessen 2026-09-08 auf `7a2794e`)

- `openapi` kommt in `.github/workflows/ci.yml` nur in Kommentarzeile 73 vor,
  in keinem Job-Schritt.
- `apps/api/tests/test_openapi_contract.py` friert **nur die Oberfläche** ein
  (Methode + Pfad + `operationId`, `_live_surface()` Z. 31–46). Schema-
  Änderungen lassen ihn grün — das ist die Lücke.
- `uv run python scripts/export_openapi.py` läuft: `OpenAPI 0.1.0: 142 Pfade`,
  Exit 0, **kein Drift** auf `7a2794e`.

### Muster-Entscheidung

**Keine Muster-Entscheidung nötig.** Das Paket fügt einen Job-Schritt in eine
bestehende Pipeline ein; es entsteht keine neue Struktur, keine Abstraktion,
kein zweiter Fall, der eine Variabilität belegen würde.

### Weichen (aus dem Issue übernommen, nicht neu entschieden)

1. Schritt im `python`-Job statt eigenem Job — Drift entsteht durch Code-
   Änderungen, und der Job läuft bei `changes.outputs.code == 'true'`.
   Ein eigener Job müsste `uv sync --group billing` duplizieren.
2. Regenerieren + `git diff --exit-code` statt Vergleichs-Test — das Generat
   ist die Wahrheit, `export_openapi.py` schreibt deterministisch.
3. Vor dem Test-Schritt — Sekunden gegen Minuten, schneller Fehlschlag spart
   den teuren Lauf. Deckt sich mit der Smoke-Budget-Norm (< 2 min).
4. `openapi_surface.json` NICHT mitregenerieren — dessen Regenerierung steht
   bewusst hinter `REGEN=1`, eine Oberflächen-Änderung soll bestätigt werden.

### Umsetzung

`.github/workflows/ci.yml`, Job `python`: neuer Schritt zwischen „Typecheck"
(`:113`) und „License check". Er ruft den Generator und prüft mit
`git diff --exit-code`; bei Abweichung nennt die Meldung das Kommando.

### Verifikation (Regel 26 — ausgeführt, nicht zitiert)

```
uv run python scripts/export_openapi.py && git diff --exit-code docs/reference/openapi.json
uv run ruff check . && uv run ruff format --check . && uv run mypy .
uv run pytest apps/api/tests/test_openapi_contract.py -q
```

Plus der vom Issue geforderte Rot-Nachweis: eine künstliche API-Änderung ohne
Regenerieren muss den Schritt rot machen.

### Schritte

- [ ] 1. Schritt in `ci.yml` einhängen
- [ ] 2. Grün-Fall lokal nachstellen (Baseline, kein Drift)
- [ ] 3. Rot-Fall lokal nachstellen (künstliche Route, nicht regeneriert)
- [ ] 4. Gates fahren, CHANGELOG, STATE, Übergabe-Bericht
- [ ] 5. PR mit `Closes #498`

### Muster-Entscheidung

**Getroffen:** drei Paare mit gleicher Semantik, aber leicht abweichendem
Wortlaut teilen sich je einen `reason`, statt sechs Gründe anzulegen.
Begründung: `reason` ist ein Maschinenvokabular für Clients, kein
Textschlüssel — zwei Gründe für dieselbe Sachlage zwingen jeden Client, beide
zu kennen. Die kompaktere Alternative (ein Grund je Stelle, mechanisch aus dem
Text abgeleitet) wurde verworfen. Belegt durch den bestehenden Vertrag: der
Client löst über `i18n.t(reason, { defaultValue: detail })` auf, `detail`
trägt die Nuance also ohnehin weiter.

**Gegenprobe zur Regel 20:** die Wiederverwendung von `agent_not_found` fiel
positiv aus (wortgleicher Text), die von `agent_persona_missing` **negativ** —
dort steht „Agent-Persona nicht gefunden (FK-Konsistenzproblem)", eine andere
Bedeutung als „Persona oder Template existiert nicht in diesem Workspace".
Deshalb `agent_reference_not_found` neu. Regel 20 wirkt also in beide
Richtungen: sie verhindert falsche Wiederverwendung *und* unnötige Dubletten.
