# Node-Version im Repo pinnen (Major 22) — Plan

Karte: `t_e2384481` · Review-Karte: `t_04ca1642` · Diagnose-Befund: `t_311fe1f2`
Owner-Entscheidung: **Option A** (Node pinnen). Option B (`execArgv: ['--no-webstorage']`)
und Option C (Vitest-5-Upgrade) sind ausdruecklich out of scope.

## Ziel

Die Node-Major, die die CI an vier Stellen in `.github/workflows/ci.yml` erzwingt
(`node-version: 22`, Zeilen 170/271/339/393), wird auch lokal verbindlich. Damit
gilt "lokal gruen = CI gruen" wieder, und `npm run test:coverage` laeuft lokal
nicht mehr in den Node-25+/Vitest-4-Defekt (`window.localStorage` undefined).

## Ausgangslage (gemessen, nicht angenommen)

| Befund | Messung |
|---|---|
| Kein Node-Pin im Repo | `ls -a` Root: kein `.nvmrc`, kein `.tool-versions`, kein `mise.toml`; `apps/web/package.json` ohne `engines` |
| CI-Major | `grep -n node-version .github/workflows/ci.yml` → 4x `22` |

| Kein Node-Hinweis in der Doku | `grep -i node CLAUDE.md` → 0 Treffer; `CONTRIBUTING.md` → 0 Treffer; `README.md:130` nennt unverbindlich "Node 22+" |

## Entscheidung 1 — welche Pin-Dateien?

Gemessen in `$TMPDIR` mit mise 2026.9.10, jeweils aus einem **Unterverzeichnis**
(damit die Vererbung mitgetestet ist):

| Variante | Datei(en) | `mise current node` | Trust noetig? |
|---|---|---|---|
| A | `.nvmrc` = `22` allein | **`26.8.2`** — Pin greift NICHT | – |
| B | `mise.toml` mit `[tools] node = "22"` | `22.23.2` | nein |
| C | `.tool-versions` mit `node 22` | `22.23.2` | nein |
| D | `.nvmrc` + `mise.toml` mit `[settings] idiomatic_version_file_enable_tools = ["node"]` | `22.23.2`, aber erst nach `mise trust` | **ja** |

Daraus folgt:

- `.nvmrc` **allein genuegt nicht** fuer den Owner: mise liest idiomatische
  Versionsdateien seit 2024 nur, wenn `idiomatic_version_file_enable_tools` das
  Tool nennt — Default ist leer (`mise settings get idiomatic_version_file_enable_tools` → `[]`).
  Variante A laeuft still in die falsche Major, also genau in den Defekt.
- Variante D haette die Version an nur einer Stelle (schoen), verlangt aber
  `mise trust`, weil eine projektlokale `[settings]`-Sektion nicht ungeprueft
  greift. Ein Entwickler, der frisch klont und nichts weiter tut, landet damit
  auf einem Fehler statt auf Node 22 — das verletzt das Akzeptanzkriterium
  "ohne Zusatzwissen".
- Gewaehlt wird **`.nvmrc` + `mise.toml` (`[tools]`)**: `.nvmrc` fuer nvm und fnm,
  `mise.toml` fuer mise (das Werkzeug des Owners) — beides trust- und
  konfigurationsfrei wirksam. `.tool-versions` waere aequivalent wirksam, ist
  aber asdfs Format; `mise.toml` ist mises natives und dokumentiertes Format.

Verbleibendes Drift-Risiko: die Zahl `22` steht in `.nvmrc`, `mise.toml` und
`engines.node`. Gemildert dadurch, dass alle drei nur die **Major** nennen und
die Begruendung zentral in `CONTRIBUTING.md` steht (siehe Entscheidung 4).

## Entscheidung 2 — welche Genauigkeit?

**Major-only (`22`)**, keine Patch-Version. Begruendung:

- Die CI pinnt selbst nur `node-version: 22` und laesst `actions/setup-node` die
  neueste 22.x ziehen. Ein Patch-Pin im Repo waere damit strikter als die CI und
  wuerde "lokal == CI" gerade wieder aufbrechen.
- Der Defekt ist eine **Major**-Eigenschaft (Web Storage per Default ab Node 25),
  kein Patch-Bug. Feiner zu pinnen loest kein Problem, erzeugt aber
  Pflegeaufwand bei jedem LTS-Patch.
- `mise` loest `22` gemessen auf `22.23.2` auf (aktuelle 22er-LTS-Linie).

## Entscheidung 3 — braucht `engines` ein `npm`-Feld?

**Nein.** Gemessen:

- `mise exec node@22 -- npm -v` → `10.9.8` (mit Node 22 gebuendelt); die CI
  bekommt via `actions/setup-node` dieselbe gebuendelte npm.
- `apps/web/package-lock.json` hat `lockfileVersion: 3` — von npm 7 bis 11
  gelesen und geschrieben. Es gibt also keine npm-Major, die `npm ci` an diesem
  Lockfile bricht.
- `engines.npm` waere ohne `engine-strict=true` (nicht gesetzt, kein `.npmrc`)
  ohnehin nur eine Warnung — ein Pin, der nichts erzwingt, ist eine zweite
  Wahrheit ohne Wirkung.

`engines.node` wird als **`>=22 <23`** gesetzt: haelt die Major fest, ohne eine
Minor zu verbieten.

## Entscheidung 4 — wo steht der Grund? (Single Source of Truth)

Genau **eine** Stelle: `CONTRIBUTING.md`, direkt in der Definition of Done, wo
`npm run test:coverage` gefordert wird — das ist der Ort, an dem der Defekt
zuschlaegt. Ein Satz plus Verweis auf Karte/PR.

`CLAUDE.md` ist fuer Agenten schreibgesperrt und braucht hier auch keinen
Eintrag: sie enthaelt bisher **null** Node-Treffer, ein zweiter Hinweis waere die
verbotene abweichende Kopie. `README.md:130` ("Node 22+") wird auf die Pin-Datei
verwiesen statt eine eigene Zahl zu behaupten.

### Fallstrick fuer den Reviewer: `mise exec` genuegt nicht immer

Der erste Lauf unter `mise exec -- npm run test:coverage` war **rot**
(135/1151, wie unter Node 26). Grund ist nicht der Pin: in einer Shell, die
`/usr/bin` schon vor mises Tool-Pfad im `PATH` hat, haengt `mise exec` seinen
Node-Pfad *hinter* `/usr/bin` (Position 14 vs. 7). Die Vitest-Worker starteten
deshalb `/usr/bin/node` v26.8.1 (Arch-Paket `nodejs 26.8.1-2`), waehrend
`node -v` in derselben Shell brav `v22.23.2` meldete. Sichtbar gemacht mit einem
Probe-Test:

```
NODE v26.8.1 execPath /usr/bin/node      # window.localStorage: undefined
NODE v22.23.2 execPath .../node/22.23.2/bin/node   # window.localStorage: object
```

Wer nachmisst, soll den Pfad also explizit voranstellen
(`export PATH="$(mise where node@22)/bin:$PATH"`) oder eine regulaer aktivierte
Shell nutzen — beides liefert dann 1151/1151. Mit `mise activate` (der normale
Entwickler-Fall) tritt das Problem nicht auf, weil die Shims dort vorne stehen.
