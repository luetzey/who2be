# Plan: Phase 2.1b-A — Status-Backend (Transitions + Draft-on-Edit + MCP-Active-Filter)

**Status:** ✅ Done — Commit `2482bd4`, gemerged via PR #46.

## Context

Phase 2.1b-0 (`feat(models,docs): VersionStatus + Dashboard-Models + ADR 0019/0020`) ist
gemergt. DB-Schema (Migrations 0011/0012), Pydantic-`VersionStatus` und Status-Felder
auf `PersonaRead`/`PlaybookRead` existieren bereits. Was fehlt: Verdrahtung der
Status-Workflow-Logik im Backend.

Diese Subphase liefert die schreibende Seite (Transitions + Draft-on-Edit) und
verdrahtet die lesende Seite (Status-Felder befuellen, MCP-Aktiv-Filter). Dashboard-
Router (`dashboard.py`) und Web-UI bleiben separat (Prompts B/C).

## Scope (aus User-Anweisung)

1. `status_history`-Repo + Service — append-only Insert via Service-Layer.
2. Transition-Endpoints `POST /v1/workspaces/{ws}/personas/{id}/versions/{v}/transition`
   und Playbook-Pendant. State-Machine in `services/version_status.py`:
   - `draft → review`
   - `review → active | draft`
   - `active → inactive`
   - `inactive → draft`
   Verbotene Uebergaenge → 409. Promotion auf `active` setzt vorherige Active-
   Version atomar auf `inactive`. `status_history`-Row in derselben Transaktion.
3. PUT-Verhalten anpassen: wenn `current_version` Status `active`, neue Version
   `current_version+1` als `draft` anlegen (Active bleibt unangetastet). Wenn bereits
   Draft existiert → 409. Bestehende Tests fuer PUT auf nicht-Active bleiben gruen.
4. `PersonaRead.current_status` + `has_pending_draft` aus DB befuellen (Repo-Joins).
   MCP-Lesepfad (`get_persona`, `list_playbooks`, `fetch_playbook`) filtert auf
   `status='active'` — Filter im Repo.

NICHT anfassen: `dashboard.py` (Prompt B), `apps/web/*` (Prompt C), neue Migrations.
RBAC verschiebt sich auf 2.3 — kein Rollen-Gate hier.

## Architektur

### State-Machine (services/version_status.py)

Single-source. Der bestehende `ALLOWED_TRANSITIONS`-Mapping in
`packages/models/.../status.py` weicht in einem Punkt vom Task ab (`inactive → draft`
fehlt, `draft → inactive` und `review → inactive` sind im Model erlaubt). Loesung:
`services/version_status.py` ist die kanonische API-State-Machine; das Model-Mapping
wird auf den Task-Spec angeglichen (zusaetzlich `inactive → draft`, dafuer keine
direkten Uebergaenge nach `inactive` ausser von `active`). Test in
`packages/models/tests/test_status.py` mitziehen.

Funktionen:
- `validate_transition(from_status, to_status) -> None` — `HTTPException 409` bei
  verbotenem Uebergang.

### WorkspaceContext-Erweiterung

`WorkspaceContext` (in `core/security.py`) bekommt `is_api_token: bool`. Wert kommt
aus `principal.token_workspace_id is not None`. Plumbing ueber `get_current_workspace`.
Services nutzen dieses Flag, um Repo-Reads auf Active-Only zu zwingen
(MCP-Pfad — Tokens sind workspace-gepinnt und werden vom MCP-Server genutzt).

### status_history (Repo + Service)

`apps/api/src/who2be_api/repositories/status_history_repository.py`:
- Protocol `StatusHistoryRepository`
- `PgStatusHistoryRepository.insert(conn, entity_type, entity_id, from_status,
  to_status, changed_by, note)` — nimmt eine explizite `asyncpg.Connection`, damit
  der Aufrufer (z.B. transition-Service) den Insert in dieselbe Transaktion
  einbetten kann.

`apps/api/src/who2be_api/services/status_history_service.py`: duenner Adapter ohne
Geschaeftslogik (nur Repo-Pass-Through; existiert primaer, um Tests gegen ein
Service-Interface schreiben zu koennen und um in Phase B/C die Dashboard-
Activity-Reads anzudocken).

### Transition-Service (services/version_status.py)

`VersionStatusService` mit Methoden:
- `transition_persona_version(ctx, persona_id, version, to, note) -> PersonaVersionRead`
- `transition_playbook_version(ctx, playbook_id, version, to, note) -> PlaybookVersionRead`

Algorithmus (pro Entity-Typ analog):
1. `BEGIN`. `SELECT pv.status FROM <entity>_version pv JOIN <entity> e ON
   e.id=pv.<entity>_id AND e.workspace_id=$ws WHERE e.id=$id AND pv.version=$v FOR
   UPDATE`. Nicht gefunden → 404.
2. `validate_transition(from, to)` → 409 bei verboten.
3. Wenn `to == 'active'`: vorhandene Active-Version dieser Entity finden und auf
   `'inactive'` setzen + zugehoerigen `status_history`-Eintrag schreiben.
4. Ziel-Version auf `to` setzen.
5. `status_history`-Eintrag fuer die durchgefuehrte Transition.
6. `COMMIT`. Geupdatete Version laden und zurueckgeben (inkl. `status`).

Konkurrenzschutz: Partial-Unique-Index auf `status='active'` erzwingt DB-seitig,
dass nie zwei Active gleichzeitig existieren — selbst wenn Schritt 3 race-t,
laesst die DB den zweiten Insert/Update mit Constraint-Violation scheitern (→ 409
mit klarer Meldung). `FOR UPDATE` plus Inactive-First-Reihenfolge minimiert das
Fenster.

### Router-Erweiterung

- `personas.py` + `playbooks.py`: neues `POST .../versions/{v}/transition`-Endpoint.
- Body: `{"to": "<status>", "note": "<optional>"}` — eigenes Pydantic-Modell
  `VersionTransitionRequest` lokal im Router (oder neues `status.py`-Modell, falls
  von Playbook + Persona geteilt — bevorzugt: in `packages/models/src/who2be_models/`).
- Router ruft `VersionStatusService.transition_*` mit `ctx`.

### Draft-on-Edit (Repository-Layer)

`PgPersonaRepository.update` umbauen:
1. `BEGIN`. Persona-Row + aktuelle Version-Status laden (`FOR UPDATE` auf persona,
   anschliessend `SELECT pv.status FROM persona_version WHERE pv.persona_id=$ AND
   pv.version=p.current_version`).
2. Wenn aktuelle Version `status='active'`:
   - Pruefen ob ein Draft existiert. Wenn ja → Repo gibt `UpdateConflict.draft`
     zurueck (neuer Result-Typ); Service mappt auf 409.
   - Sonst: neue Version `current_version+1` mit `status='draft'` einfuegen,
     Persona-`current_version` updaten.
3. Wenn aktuelle Version nicht active: bestehende Logik (neue Version mit
   Default-Status `'inactive'`).

Repository-Return: Statt `PersonaRead | None` ein Result-Typ:
```python
@dataclass(frozen=True)
class UpdateOutcome:
    persona: PersonaRead | None
    conflict: Literal["draft_exists"] | None = None
```
oder einfacher: `PersonaRead | UpdateConflict`. Wir waehlen den klareren Discriminator
ueber ein kleines Result-Objekt — der Service uebersetzt in 404/409.

Playbook-Repo analog.

### MCP-Active-Filter im Repo

`PersonaRepository.fetch` / `.list_by_workspace` und `PlaybookRepository.fetch` /
`.list_by_workspace` und `PersonaPlaybookRepository.list_linked` bekommen einen
neuen Parameter `active_only: bool`. Effekt:
- Statt `JOIN ON pv.version = p.current_version` → `JOIN ON pv.status = 'active'`.
- `current_version` wird im SELECT durch `pv.version` ersetzt — der MCP-Konsument
  sieht eine konsistente Active-Version (current_version und content matchen).
- Eintraege ohne Active-Version werden ausgefiltert.

Service-Layer (`PersonaService`, `PlaybookService`, `PersonaPlaybookService`) liest
`ctx.is_api_token` und reicht es als `active_only` an die Repo durch. Der Path
`get_persona` (Persona-Detail) + `_resolve_persona_by_name` + `list_playbooks` +
`fetch_playbook` decken die im Task genannten MCP-Tools ab. `get_persona` (MCP)
ruft zusaetzlich `get_persona_playbooks` — auch dort active_only setzen.

### current_status + has_pending_draft befuellen

In `_SELECT_CURRENT` (persona & playbook) zusaetzlich aufnehmen:
- `cv.status AS current_status`
- `EXISTS (SELECT 1 FROM <entity>_version dv WHERE dv.<entity>_id = p.id AND
  dv.status='draft') AS has_pending_draft`

`PersonaRead`/`PlaybookRead` haben die Felder bereits; `model_validate` fuellt sie
aus dem Row-Dict. Default-Werte bleiben fuer INSERT/UPDATE-Returns (wo wir
unmittelbar den frischen Stand kennen und keine zusaetzlichen Subqueries brauchen):
- INSERT: `current_status='inactive'`, `has_pending_draft=False` (neu erzeugte v1
  ist per DB-Default `'inactive'`, keine andere Version → kein Draft).
- UPDATE-non-active-Pfad: `current_status='inactive'`, `has_pending_draft=False`
  fuer den Standard-Fall; bei Edge-Cases (alter Draft im System) ggf. neu querien —
  einfacher: nach UPDATE/Draft-Create immer per `fetch` re-querien (kostet einen
  Roundtrip, ist aber konsistent und einfacher zu testen).

**Entscheidung:** Nach INSERT/UPDATE einmal per `fetch` re-querien — Konsistenz vor
Roundtrip-Sparsamkeit, der Pfad ist nicht hot.

## Offene Fragen / Trade-offs

- **ALLOWED_TRANSITIONS-Konflikt:** Model-Layer hatte `draft→inactive` und
  `review→inactive` erlaubt; Task-Spec hat sie nicht. Wir folgen Task-Spec und
  passen Model + Tests an. Begruendung: Task ist explizit und neuer, Model wurde
  in Prompt 0 nur als Skelett gesetzt.
- **`is_api_token`-Plumbing:** WorkspaceContext ist die Service-Sicht. Alternative
  waere ein separates `ReadMode`-Enum — zu viel Abstraktion fuer eine einzige
  Bool-Property. `is_api_token` ist klar lesbar.
- **Re-query nach INSERT/UPDATE:** Pragmatisch fuer Konsistenz. Wenn Performance
  in Phase 2.3+ knapp wird, kann RETURNING erweitert werden.
