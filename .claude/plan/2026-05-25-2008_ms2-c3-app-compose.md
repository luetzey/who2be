# Plan: MS-2 C3 — App-Compose (API + MCP + Web) + Reverse-Proxy (Hetzner)

## Context

Roadmap-Verweis: `.claude/plan/2026-05-24_who2be-mvp-roadmap.md` §MS-2 C3 — Outcome:

> Caddy (oder Traefik) terminiert HTTPS via Lets-Encrypt auf zwei Subdomains;
> API-Container fuehrt beim Boot `who2be-migrate` aus; MCP-Container faehrt mit
> `WHO2BE_API_BASE_URL` auf die interne API-Adresse; Web-Container serviert das
> Vite-Build statisch.

H3 (Security-Review) ist via PR #12 in `main` (Commit `5fa619f`). Aus
`docs/security-findings.md` sind **F-02 (High)** und **F-12 (Info)** explizit
als Akzeptanzkriterien fuer C3 markiert — der Stack erfuellt beide durch
`--proxy-headers --forwarded-allow-ips *` an uvicorn und ein
Security-Header-Snippet im Caddyfile.

C3 baut **nur** Build-/Compose-Artefakte. Es deployt nichts (= C4),
provisioniert keinen Server (= C1), enthaelt kein Supabase-Compose (= C2)
und kein Backup-Skript (= C5). Verifikation laeuft komplett lokal via
`docker compose build` + Smoke-Variante mit Override-File.

## Approach (Designentscheidungen)

### 1. Reverse-Proxy: Caddy (`caddy:2.8-alpine`)

Auto-HTTPS via Lets-Encrypt out of the box, fuenf Zeilen pro Site, kein
separater `traefik.yml`. Konsistent mit dem ADR-Stil "Werkzeug, das in
wenigen Zeilen das Noetige tut".

### 2. MCP-Container: ja, aber `profile: mcp`

User-Entscheidung: das Image wird gebaut, auch wenn der Default-Transport
des FastMCP-Servers stdio ist und der Container damit nicht reverse-proxy-fest
laeuft. Pragmatischer Zwischenweg:
- Eigenes `apps/mcp/Dockerfile` (minimaler als API-Image: nur `apps/mcp` +
  `packages/models`, ohne asyncpg/uvicorn-Footprint).
- Im Hetzner-Compose unter `profiles: ["mcp"]` — wird nicht beim normalen
  `docker compose up` gestartet, ist aber per `docker compose run --rm mcp
  who2be-mcp` als interner API-Consumer-/Smoke-Harness aufrufbar. Bereitet
  zugleich C4 vor (Image kann via GHCR getaggt werden).
- Wenn spaeter ein Remote-MCP-HTTP-Transport eingefuehrt wird, kippt das
  Profil auf `default` — keine weitere Strukturaenderung noetig.

### 3. Web-Container: `nginx:1.27-alpine` mit Multi-Stage-Build

Konsistent mit dem bestehenden `auth-gateway`-Image. Build-Args durch
`VITE_API_BASE_URL`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`
durchreichen (Compile-Time-Substitution, `apps/web/src/config.ts:14-23`
wirft im PROD-Mode bei leer — gewuenschter Fail-Fast). Eigene `nginx.conf`
mit SPA-Fallback (`try_files $uri /index.html`).

### 4. Migrations beim Boot: Init-Container-Pattern aus Root-Compose

1:1 portiert: dedizierter `migrate`-Service mit `restart: "no"`,
`command: ["who2be-migrate"]`, nutzt dasselbe Image wie API. API haengt
ueber `depends_on.migrate.condition: service_completed_successfully`.

### 5. Image-Naming fuer C4

- `api` / `migrate` → `ghcr.io/luetzey/who2be-api:${API_IMAGE_TAG:-latest}`
- `web` → `ghcr.io/luetzey/who2be-web:${WEB_IMAGE_TAG:-latest}`
- `mcp` → `ghcr.io/luetzey/who2be-mcp:${MCP_IMAGE_TAG:-latest}`
- `caddy` → upstream `caddy:2.8-alpine` (kein Build)

Compose-File traegt `image:` UND `build:`, sodass C4 spaeter nur den
`docker compose pull` + `up -d` Schritt ergaenzen muss.

## File-by-file Changes

### A. `apps/api/Dockerfile` — angepasst

1. **Non-root User** vor `EXPOSE`:
   ```
   RUN useradd --system --no-create-home --uid 1000 who2be \
       && chown -R who2be:who2be /app
   USER who2be
   ```
2. **`HEALTHCHECK`-Direktive** (curl ist schon installiert):
   ```
   HEALTHCHECK --interval=15s --timeout=5s --start-period=10s --retries=3 \
     CMD curl -fsS http://localhost:8000/v1/health || exit 1
   ```
3. **`CMD` mit Proxy-Args** (F-02):
   ```
   CMD ["uvicorn", "who2be_api.main:app", "--host", "0.0.0.0", "--port", "8000",
        "--proxy-headers", "--forwarded-allow-ips", "*"]
   ```
   `*` ist sicher, weil der Container im internen Compose-Netzwerk keinen
   `ports:`-Eintrag hat und nur Caddy ihn erreicht.

### B. `apps/web/Dockerfile` — Rewrite

```Dockerfile
FROM node:22-slim AS builder
WORKDIR /app
COPY apps/web/package.json apps/web/package-lock.json ./
RUN npm ci
COPY apps/web/ ./
ARG VITE_API_BASE_URL
ARG VITE_SUPABASE_URL
ARG VITE_SUPABASE_ANON_KEY
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL \
    VITE_SUPABASE_URL=$VITE_SUPABASE_URL \
    VITE_SUPABASE_ANON_KEY=$VITE_SUPABASE_ANON_KEY
RUN npm run build

FROM nginx:1.27-alpine AS runtime
RUN apk add --no-cache curl
COPY --from=builder /app/dist /usr/share/nginx/html
COPY apps/web/nginx.conf /etc/nginx/conf.d/default.conf
HEALTHCHECK --interval=15s --timeout=5s --start-period=5s --retries=3 \
  CMD curl -fsS http://localhost/healthz || exit 1
EXPOSE 80
```

### C. `apps/web/nginx.conf` — NEU

```nginx
server {
    listen 80;
    server_name _;
    root /usr/share/nginx/html;
    index index.html;

    location / { try_files $uri $uri/ /index.html; }
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
    location = /healthz {
        access_log off;
        default_type text/plain;
        return 200 "ok\n";
    }
}
```

### D. `apps/mcp/Dockerfile` — NEU

```Dockerfile
# Build-Context = Repo-Root (siehe apps/api/Dockerfile fuer Begruendung).
FROM python:3.11-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:0.4.27 /uv /usr/local/bin/uv
WORKDIR /app
ENV UV_LINK_MODE=copy UV_COMPILE_BYTECODE=1
COPY pyproject.toml uv.lock ./
COPY packages packages
COPY apps/api apps/api
COPY apps/mcp apps/mcp
# Gleicher Workspace-Sync wie API — der uv-Workspace verlangt alle Member.
RUN uv sync --frozen

FROM python:3.11-slim AS runtime
WORKDIR /app
ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
COPY --from=builder /app /app
RUN useradd --system --no-create-home --uid 1000 who2be \
    && chown -R who2be:who2be /app
USER who2be
CMD ["python", "-m", "who2be_mcp.server"]
```

Begruendung: Eigenes Dockerfile statt API-Image-Reuse, damit das MCP-Image
einen klaren Identitaets- und Versions-Hook fuer C4 hat. Footprint bleibt
hoch (gleicher uv-Sync), aber das ist OK fuer Phase 0; Slim-Variante kann
spaeter via `runtime`-uv-Group ueberlagert werden (gleiches Followup wie
beim API-Image).

### E. `deploy/hetzner/who2be/docker-compose.yml` — NEU

Services `migrate`, `api`, `mcp` (Profile `mcp`), `web`, `caddy`. Networks
`app-net` (intern) und `supabase-net` (extern, von C2 angelegt). Volumes
fuer Caddy. Env-Vars aus `deploy/hetzner/.env`. Detail siehe unten im
Implementations-Schritt.

### F. `deploy/hetzner/Caddyfile` — NEU

Reusable `(security_headers)`-Snippet mit HSTS, X-Content-Type-Options,
X-Frame-Options, Referrer-Policy, `-Server`. `api.{$DOMAIN}` → `api:8000`
mit JSON-only-CSP. `app.{$DOMAIN}` → `web:80` mit SPA-CSP
(`script-src 'self'`, `connect-src` auf eigene API + Supabase).

### G. `deploy/hetzner/.env.example` — NEU

Alle Env-Vars, die der Operator setzen muss: `DOMAIN`, `ACME_EMAIL`,
`API_IMAGE_TAG`, `WEB_IMAGE_TAG`, `MCP_IMAGE_TAG`, `DATABASE_URL`,
`JWT_SECRET`, `SUPABASE_URL`, `CORS_ORIGINS`, `VITE_API_BASE_URL`,
`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `WHO2BE_API_TOKEN`
(fuer MCP-Profile).

### H. `deploy/hetzner/README.md` — NEU

Run-Anleitung: Voraussetzungen (C1 + C2), `.env`-Setup, Build/Pull,
`up -d --wait`, Smoke gegen `https://api.<domain>/v1/health`, Logs,
Caddy-Validate. Verweis auf C5-RUNBOOK fuer Backup/Restore.

### I. `deploy/hetzner/who2be/docker-compose.local.yml` — NEU

Override-File fuer lokale Smoke ohne C2/Hetzner:
- Spinnt einen lokalen `db` (`postgres:16`) im `supabase-net` an.
- Mappt Caddy-Port nicht 443, sondern Test-Port 8080.
- Erlaubt `docker compose -f who2be/docker-compose.yml -f
  who2be/docker-compose.local.yml --env-file ../.env up -d --wait`.

### J. `.dockerignore` — Eventuell anpassen

Aktueller Stand schliesst `.git`, `.claude`, `.venv`, `node_modules`,
`dist`, `__pycache__` aus — passt fuer beide Dockerfiles. Pruefen, ob
`apps/web/dist` und Test-Output nicht doch in den Web-Build-Context
sickern.

## Wiederverwendung

| Quelle                                                                            | C3-Nutzung                                                                |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Bestehendes `apps/api/Dockerfile` (uv-multi-stage)                                 | Behalten, +3 Anpassungen (Healthcheck, Non-root, Proxy-Args).             |
| Root `docker-compose.yml:26-36` (Migrate-Init-Container)                          | 1:1 nach `deploy/hetzner/who2be/docker-compose.yml`.                       |
| `apps/api/src/who2be_api/core/migrations.py` (`who2be-migrate`-CLI)               | Wird vom Migrate-Container aufgerufen — null Code-Aenderung.              |
| `apps/api/src/who2be_api/core/config.py` (`CORS_ORIGINS` CSV-Support)             | Operator setzt `CORS_ORIGINS=https://app.<domain>`.                       |
| `apps/web/src/config.ts:14-23` (PROD-Throw bei leerem `VITE_*`)                   | Wirft beim Build, falls Build-Args fehlen — Fail-Fast.                     |
| `supabase/gateway.conf`                                                            | Stil fuer `apps/web/nginx.conf` (Aufbau, nicht Inhalt).                    |
| `apps/api/src/who2be_api/main.py` (`SlowAPIMiddleware`, `RequestIDMiddleware`)    | Unveraendert. F-02-Mitigation laeuft nur ueber `uvicorn`-CMD-Args.         |

Nicht wiederverwendet:
- Hot-Reload-Volume aus `docker-compose.yml:111-113`.
- `JWT_SECRET`-Default `dev-jwt-secret-change-me-32chars-min` — in
  `deploy/hetzner/.env.example` ist die Var ohne Default; Operator
  **muss** sie setzen, sonst Lifespan-Crash (F-08-Patch).

## Verifikation

Reihenfolge so, dass alles ohne Hetzner-Server lokal laeuft:

1. **Caddyfile-Syntax** (offline):
   ```
   docker run --rm \
     -v $(pwd)/deploy/hetzner/Caddyfile:/etc/caddy/Caddyfile:ro \
     -e DOMAIN=localhost.test -e ACME_EMAIL=test@example.com \
     -e VITE_SUPABASE_URL=http://localhost:9999 \
     caddy:2.8-alpine caddy validate \
       --config /etc/caddy/Caddyfile --adapter caddyfile
   ```
2. **Lokale Builds**:
   ```
   cp deploy/hetzner/.env.example deploy/hetzner/.env
   docker compose -f deploy/hetzner/who2be/docker-compose.yml \
     --env-file deploy/hetzner/.env build api web
   docker compose -f deploy/hetzner/who2be/docker-compose.yml \
     --profile mcp --env-file deploy/hetzner/.env build mcp
   ```
3. **Lokaler Smoke mit Override**:
   ```
   docker compose -f deploy/hetzner/who2be/docker-compose.yml \
                  -f deploy/hetzner/who2be/docker-compose.local.yml \
                  --env-file deploy/hetzner/.env up -d --wait
   curl -fsS http://localhost:8080/v1/health
   docker compose ... down -v
   ```
4. **Python-Stack** unbeeintraechtigt:
   `uv run ruff check . && uv run ruff format --check . && uv run mypy .
   && uv run pytest -q`.
5. **Web-Stack** unbeeintraechtigt:
   `cd apps/web && npm run lint && npx tsc --noEmit && npm test`.
6. **CI**: `.github/workflows/ci.yml` bleibt unangetastet. `compose-smoke`-Job
   nutzt das Root-Compose, nicht das Hetzner-Compose.

## Out of Scope (bewusst)

- **C1** — Hetzner-Server-Provisioning (Firewall, SSH).
- **C2** — Self-hosted Supabase-Compose.
- **C4** — `.github/workflows/deploy.yml`, GHCR-Push, SSH-Deploy.
- **C5** — Backup-Cron + RUNBOOK.
- **C6** — E2E-Smoke gegen produktive Instanz.
- **MCP-HTTP-Transport** — Default bleibt stdio, Container im
  `mcp`-Profil als interner Consumer/Test-Harness.
- **Runtime-uv-Group** fuer Prod-Image-Slim — `# fuer Prod-Image
  spaeter eigene runtime-Group anlegen`-TODO aus
  `apps/api/Dockerfile:23` bleibt; eigene Refactor-Task.
