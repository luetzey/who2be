## Kontext

Phase 2.3 (Multi-User pro Workspace) braucht zwei Schema-Bausteine, bevor
Endpoints, geschaerfte `get_current_workspace` und Frontend kommen koennen:

1. **Invitations** — `workspace_invitation`-Tabelle (Token nur als Hash,
   Klartext geht per Mail raus). Existiert heute noch nicht (ADR-0019 §Kons.).
2. **Token-Role-Snapshot** — API-Token bekommt eine `role`-Spalte, die die
   Rolle des Erstellers zum Erstellungszeitpunkt pinnt. Verhindert
   Privilege-Drift (Token erbt nicht automatisch hoehere Rechte, wenn der
   Ersteller spaeter promotet wird).

Dies ist die **Models+Schema+ADR-only**-PR (analog 2.1b-0). Bewusst NICHT
in dieser PR: `get_current_workspace` verschaerfen, neue Endpoints,
Frontend. Bestehende Tests muessen gruen bleiben — der Backfill-Default der
neuen Token-Rolle ist `admin`, damit Bestands-Token funktional unveraendert
bleiben.

## Scope / Umsetzung

### 1. Migration `0017_workspace_invitation.sql`

`workspace_invitation`:
- `id uuid PK DEFAULT gen_random_uuid()`
- `workspace_id uuid NOT NULL REFERENCES workspace(id) ON DELETE CASCADE`
- `email text NOT NULL`
- `role text NOT NULL CHECK (role IN ('admin','editor','viewer'))`
- `token_hash text NOT NULL UNIQUE` — nur Hash (ADR-0006-Linie, analog
  `api_token.token_hash`); Klartext geht per Mail.
- `expires_at timestamptz NOT NULL`
- `created_by uuid NOT NULL`
- `accepted_at timestamptz` (nullable)
- `revoked_at timestamptz` (nullable)
- `created_at timestamptz NOT NULL DEFAULT now()`

Index: **partial unique** auf `(workspace_id, lower(email))`
`WHERE accepted_at IS NULL AND revoked_at IS NULL` — verhindert zwei offene
Invitations fuer dieselbe Mail im selben Workspace (Replay/Doppel-Invite).
Plus ein Lookup-Index ist durch `token_hash UNIQUE` schon abgedeckt.

Neu erstellte Migration ist trivially idempotent ueber den Runner
(`schema_migrations`); fuer manuelles Re-Apply (Phase-Idempotenztest)
`CREATE TABLE IF NOT EXISTS` + `CREATE ... INDEX IF NOT EXISTS`.

### 2. Migration `0018_api_token_role_snapshot.sql`

`ALTER TABLE api_token ADD COLUMN role ...` mit
`CHECK (role IN ('admin','editor','viewer')) NOT NULL DEFAULT 'admin'`.
Bestehende Token bekommen per Default `admin` (funktional unveraendert).

Idempotent: `ADD COLUMN IF NOT EXISTS`. Der CHECK-Constraint ist Teil der
Spaltendefinition und kommt mit `IF NOT EXISTS` nur beim ersten Lauf.

### 3. Models (`packages/models/src/who2be_models/`)

- **`workspace_member.py`** (neu):
  - `WorkspaceRole(StrEnum)` `{admin, editor, viewer}` — Single-Source der
    Rollen-Hierarchie.
  - `WorkspaceMemberRead` (`workspace_id`, `user_id`, `role`, `joined_at`,
    `from_attributes=True`).
  - `WorkspaceMemberUpdate` (nur `role`, `extra="forbid"`).
- **`invitation.py`** (neu):
  - `InvitationCreate` (`email: EmailStr`, `role: WorkspaceRole`,
    `extra="forbid"`).
  - `InvitationRead` (`id`, `email`, `role`, `expires_at`, `created_at`,
    `from_attributes=True`) — **kein** `token_hash`/Klartext im Read.
  - `InvitationAccept` (`token: str`, `extra="forbid"`).
- **`token.py`** (erweitern):
  - `TokenRead` bekommt `role: WorkspaceRole`.
  - `TokenCreate` bekommt `role: WorkspaceRole | None = None` — Default
    `None` ⇒ Service setzt die aktuelle Rolle des Erstellers (Snapshot).
    Pydantic-Layer schreibt die Drift-Semantik nicht durch; das macht der
    Service in einer spaeteren PR.
- **`__init__.py`**: neue Symbole exportieren (`WorkspaceRole`,
  `WorkspaceMemberRead`, `WorkspaceMemberUpdate`, `InvitationCreate`,
  `InvitationRead`, `InvitationAccept`) + `__all__` sortiert.

`EmailStr` braucht `pydantic[email]` — pruefen, ob `email-validator` schon
in den Deps ist; sonst Fallback auf `str` mit Pattern-Constraint (kein neuer
Dep-Zwang in einer reinen Models-PR).

### 4. ADR `docs/adr/0023-multi-user-rbac.md` (Stil 0019/0020)

- Rollen-Hierarchie `admin > editor > viewer` + Permission-Matrix pro Rolle
  (Drafts create/edit/delete, transition-Stufen, member-Verwaltung,
  token-CRUD).
- Token-Snapshot-Rolle: Token-Verhalten gepinnt auf `created_by_role`, nicht
  dynamisch. Trade-off: verhindert Privilege-Drift, aber Token bleibt aktiv,
  wenn der User downgegradet wird → muss explizit revoked werden. Begruenden.
- Promote-to-Active nur durch `admin` (Reviewer-Rolle); `editor` kann
  Draft→Review pushen, nicht Review→Active.
- Invitation-Hash-only + Single-Use + Expiry (Replay-Schutz).
