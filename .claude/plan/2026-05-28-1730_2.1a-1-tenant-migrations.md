# Plan: Phase 2.1a-1 — Datenmodell + Migrations (TASK-300)

**Status:** ✅ Done — Commit `9e35449`, gemerged via PR #38.

## Context

Who2Be ist heute ein Single-User-System: alle Daten sind ueber `owner_id` (Supabase-User-UUID) isoliert. Damit das Produkt zur **vollwertigen Multi-Tenant-App** wird, brauchen wir die Hierarchie `User → org_member → Organization → Workspace → Entity` und einen **Status-Workflow pro Version** (Draft / Review / Active / Inactive). Phase 2.1 aus `.claude/plan/2026-05-27-1921_phase-2-vollwertige-app.md` zerlegt das in sechs Sub-Tasks (2.1a-1..6). Diese Plan-Datei beschreibt nur **2.1a-1** — den DB-Layer plus Backfill plus Migration-Tests. Repos, Services, Router, Web und MCP-Pfade kommen in den folgenden Sub-Tasks (insbesondere 2.1a-2 = TASK-301), ADRs in 2.1a-6 (TASK separat).

**Outcome:** Migrations 0005-0013 sind im Repo, laufen idempotent gegen die Postgres-CI-DB, und ein neuer Integration-Test belegt Idempotenz + Backfill-Cardinality + die DB-Invarianten der neuen Status-Spalten. Existierender Code (Repos, Services, Router, Tests) bleibt unveraendert lauffaehig — der Schema-Lock auf `workspace_id NOT NULL` + Composite-FK-Switch in `persona_playbook` wird bewusst nach 2.1a-2 verschoben (Begruendung siehe unten).

## Architektur-Entscheidungen

- **Disjunkter Schnitt 2.1a-1 vs. 2.1a-2:** 2.1a-1 fuegt die neuen Tabellen + nullable `workspace_id` + Backfill der Daten hinzu. `SET NOT NULL`, `UNIQUE(workspace_id, id)` und der Composite-FK-Switch in `persona_playbook` (von `(owner_id, persona_id) → persona(owner_id, id)` auf `(workspace_id, persona_id) → persona(workspace_id, id)`) leben in **0014_finalize_workspace_id.sql** und werden in 2.1a-2 zusammen mit dem Repository-Refactor (`persona_playbook_repository.set_links` schreibt `workspace_id`, `_SELECT_CURRENT` filtert auf `workspace_id`) geliefert. Grund: der heutige Repo-Code in `apps/api/src/who2be_api/repositories/persona_playbook_repository.py:99-104` setzt `(persona_id, playbook_id, owner_id)` ohne `workspace_id`; ein FK-Switch in 2.1a-1 wuerde alle Integration-Tests in `test_personas.py` / `test_playbooks.py` / `test_persona_playbooks.py` rot machen, ohne dass der zugehoerige Code-Refactor in derselben Sub-Task liegt. Plan-Vorlage §2.1.A ("`ADD COLUMN nullable, Backfill, dann NOT NULL`") wird damit nicht verletzt, nur ueber zwei Sub-Tasks verteilt.
- **`owner_id` bleibt als Audit-Spalte** auf `persona`/`playbook`/`api_token`/`persona_playbook` — Plan-Vorlage §2.1.A explizit ("bitter zu droppen, billig zu behalten"). Wird zur Anzeige in `status_history.changed_by`-Default-Linie und ist die Bruecke fuer den Backfill.
- **`status`-Spalte als TEXT mit CHECK-Constraint**, nicht als Postgres-Enum. Konsistent mit dem heutigen Code-Pattern (siehe `apps/api/src/who2be_api/migrations/0003_playbook.sql` — `type text`, `tags text[]`), erspart `ALTER TYPE`-Rituale bei spaeteren Erweiterungen und passt zur Pydantic-V2-Konvention (kein Enum in den Models, siehe `packages/models/src/who2be_models/playbook.py`).
- **Partial Unique Indices pro Status-Slot**: `CREATE UNIQUE INDEX ... ON persona_version (persona_id) WHERE status='active'` (analog `draft` und `review`) — DB-erzwungene Invariante "max. 1 Draft / 1 Review / 1 Active pro Entity". Pattern aus Plan §2.1.A.
- **Backfill-Cardinality**: pro distinct `owner_id` ueber `persona ∪ playbook ∪ api_token` wird genau eine Personal-`organization` (kind='personal') angelegt, genau ein `workspace` ("Personal") darin und genau ein `workspace_member` mit Rolle `admin`. Damit ist die Hierarchie fuer 2.1a-2 lese- und schreibbar — und 2.3 braucht keinen Backfill mehr (Plan §2.1.A 0007-Hinweis).
- **`status_history` ist append-only Audit**, getrennt vom Version-Bump (Plan §2.1.A). Schema folgt der Plan-Vorlage: `(entity_type, entity_id, from_status, to_status, changed_by, changed_at, note)`. Schreibt Code erst in 2.1b-1 (Status-Endpoints).

## Migrations (neu in `apps/api/src/who2be_api/migrations/`)

Sequenz folgt der Plan-Vorlage §2.1.A. Vorlage fuer Composite-FK-Pattern: `0004_persona_playbook.sql:9-19`.

- **0005_organization.sql**
  - `organization(id uuid PK, name text NOT NULL, slug text NOT NULL, kind text NOT NULL CHECK (kind IN ('personal','company')), created_at timestamptz DEFAULT now())`
  - Unique `(kind, slug)` damit Personal-Slugs nicht mit Company-Slugs kollidieren
  - `org_member(org_id uuid REFERENCES organization(id) ON DELETE CASCADE, user_id uuid NOT NULL, role text NOT NULL CHECK (role IN ('owner','admin','member')), invited_by uuid, joined_at timestamptz DEFAULT now(), PRIMARY KEY (org_id, user_id))`
- **0006_workspace.sql**
  - `workspace(id uuid PK, org_id uuid REFERENCES organization(id) ON DELETE CASCADE, name text NOT NULL, slug text NOT NULL, created_at timestamptz DEFAULT now())`
  - Unique `(org_id, slug)`; Index `(org_id)` fuer org-scoped Lookups
- **0007_workspace_member.sql**
  - `workspace_member(workspace_id uuid REFERENCES workspace(id) ON DELETE CASCADE, user_id uuid NOT NULL, role text NOT NULL CHECK (role IN ('admin','editor','viewer')), joined_at timestamptz DEFAULT now(), PRIMARY KEY (workspace_id, user_id))`
  - Tabelle existiert schon ab 2.1, wird in 2.1 nur fuer den Personal-Workspace-Owner gefuellt, in 2.3 echt benutzt.
- **0008_persona_workspace.sql**
  - `ALTER TABLE persona ADD COLUMN workspace_id uuid REFERENCES workspace(id) ON DELETE CASCADE`
  - `CREATE INDEX persona_workspace_id_idx ON persona (workspace_id)`
  - (kein NOT NULL, kein UNIQUE(workspace_id, id) — Lock kommt in 0014)
- **0009_playbook_workspace.sql** — analog 0008 fuer `playbook`.
- **0010_api_token_workspace.sql** — analog 0008 fuer `api_token`. (Workspace-pro-Token-Scope laut Plan §2.1.D.)
- **0011_status_on_versions.sql**
  - `ALTER TABLE persona_version ADD COLUMN status text NOT NULL DEFAULT 'inactive' CHECK (status IN ('draft','review','active','inactive'))`
  - Analog `playbook_version`
  - **Backfill in derselben Migration:** `UPDATE persona_version pv SET status='active' FROM persona p WHERE pv.persona_id = p.id AND pv.version = p.current_version` (alle anderen bleiben auf Default 'inactive'). Analog Playbooks.
  - **Partial Unique Indices** je Entity-Typ: `CREATE UNIQUE INDEX persona_version_active_uniq ON persona_version (persona_id) WHERE status = 'active'`; analog `draft` und `review`; analog Playbook.
- **0012_status_history.sql**
  - `status_history(id uuid PK DEFAULT gen_random_uuid(), entity_type text NOT NULL CHECK (entity_type IN ('persona','playbook','resource')), entity_id uuid NOT NULL, from_status text, to_status text NOT NULL, changed_by uuid NOT NULL, changed_at timestamptz NOT NULL DEFAULT now(), note text)`
  - `entity_type` enthaelt schon `'resource'` als zulaessigen Wert (Vorgriff fuer 2.2 — billig).
  - Index `(entity_type, entity_id, changed_at DESC)` fuer Dashboard-Activity-Queries (Plan §2.1.E).
- **0013_backfill_tenants.sql** — **kein Schema-Lock, nur Daten + Mitgliedschaft.**
  - `CREATE TEMP TABLE _owner_ids ON COMMIT DROP AS SELECT DISTINCT owner_id FROM persona UNION SELECT DISTINCT owner_id FROM playbook UNION SELECT DISTINCT owner_id FROM api_token`
  - Pro Owner: `INSERT INTO organization` (kind='personal', slug aus owner_id Hex-Prefix), `INSERT INTO org_member` (role='owner'), `INSERT INTO workspace` (name='Personal'), `INSERT INTO workspace_member` (role='admin')
  - Idempotenz: `ON CONFLICT (kind, slug) DO NOTHING` auf organization; nachgelagerte Inserts mit `WHERE NOT EXISTS`-Guard. Damit ist der zweite Migration-Lauf no-op.
  - `UPDATE persona p SET workspace_id = w.id FROM workspace w JOIN org_member om ON om.org_id = w.org_id WHERE p.owner_id = om.user_id AND p.workspace_id IS NULL`. Analog `playbook`, `api_token`.
  - `persona_playbook` braucht in 2.1a-1 **noch keine** `workspace_id`-Spalte (kommt in 0014).

## Test (neu)

`apps/api/tests/test_phase21_migrations.py` — Pattern aus `apps/api/tests/test_migrations.py:42-66` (`_db_reachable`-Skip, `apply_migrations(tmp_path)` mit kopierten SQL-Files):

- **test_phase21_idempotent** — kopiert alle SQL-Files (0001-0013) nach `tmp_path`, ruft `apply_migrations` zweimal auf, erwartet alle Filenamen im ersten Lauf und `[]` im zweiten.
- **test_phase21_tables_created** — nach voller Migration sind `organization`, `org_member`, `workspace`, `workspace_member`, `status_history` in `information_schema.tables` (analog `test_core_migrations_create_all_tables` bei `test_migrations.py:69-88`).
- **test_phase21_status_invariant** — INSERT in `persona_version` mit `status='active'` zweimal fuer dieselbe `persona_id` schlaegt mit `UniqueViolationError` fehl. Analog `status='draft'` und `status='review'`.
- **test_phase21_status_backfill** — nach Migration `SELECT status FROM persona_version WHERE persona_id = X AND version = current_version` liefert `'active'`, andere Versionen `'inactive'`. (Pre-Seed in 0001-0004 Phase, dann 0011 anwenden — siehe Pattern unten.)
- **test_phase21_backfill_cardinality** — zwei-Stufen-Apply: (a) kopiere nur 0001-0004 nach `tmp_path`, `apply_migrations`, seede drei distinct `owner_id`s ueber `persona`/`playbook`/`api_token`-Inserts; (b) kopiere 0005-0013 nach `tmp_path` dazu, `apply_migrations` erneut. Dann: `SELECT count(*) FROM organization WHERE kind='personal'` == 3, `SELECT count(*) FROM workspace` == 3, `SELECT count(*) FROM workspace_member WHERE role='admin'` == 3, jede `persona.workspace_id` ist nicht NULL und zeigt auf den richtigen Workspace.
- **Cleanup zwischen Tests**: pro Test eigene `_db_reachable`-Pruefung, Tabellen-Drop am Ende via `DROP TABLE IF EXISTS ... CASCADE` und Loeschen aus `schema_migrations` (analog `test_migrations.py:58-61`). Reihenfolge: zuerst neue Tabellen droppen, dann persona/playbook/api_token leeren, damit die Test-Reihenfolge robust ist.
