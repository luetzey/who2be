## Kontext

2.3-0 hat Schema + Modelle geliefert, Enforcement aber bewusst ausgeklammert.
`get_current_workspace` liest heute zwar schon `workspace_member.role`, gibt
die Rolle aber als `Literal[...]` zurueck und wertet sie nirgends aus: jeder
Member darf faktisch alles. Diese Stufe macht daraus echte Autorisierung
gemaess ADR-0023 + setzt den Token-Role-Snapshot durch.

**Policy-Klaerung (mit User bestaetigt):** Bei Konflikt zwischen Task-Wortlaut
und ADR-0023 gilt die ADR. Konkret:
- Token-CRUD (create/list/revoke) = **editor+** (nicht admin-only).
- Transition `review → draft` (Reject/Bounce) = **editor+** (nicht admin-only).
Damit ist `viewer` voll read-only **ausser** Token-Listing (ADR Zeile 73:
viewer ❌ fuer Token) — Token-GET ist editor+.

## Permission-Matrix (ADR-0023, maßgeblich)

| Aktion | min. Rolle |
|---|---|
| Personas/Playbooks/Resources/Dashboard **lesen** | viewer |
| Member **listen** | viewer |
| Draft create/update/delete, Link-Setter | editor |
| Transition `draft→review`, `review→draft`, `inactive→draft` | editor |
| Transition `review→active` (Promote), `active→inactive` (Retire) | admin |
| Token create/list/revoke | editor |
| Member invite / role / remove, Invitation create | admin |

Ableitung Transition-Gate: `admin` gdw. `to_status ∈ {active, inactive}`,
sonst `editor`.

## Scope / Umsetzung

### 1. `core/security.py`

- `WorkspaceContext.role: WorkspaceRole` (statt `Literal[...]`).
- `CurrentPrincipal.token_role: WorkspaceRole | None` (None im JWT-Pfad,
  gesetzt aus `api_token.role` im Token-Pfad).
- `_ROLE_ORDER` + `role_satisfies(actual, min)` + `require_role(ctx, min) -> 403`.
- `get_current_workspace` zweigeteilt:
  - **API-Token-Pfad** (`token_workspace_id is not None`): Workspace-Pin
    pruefen (Mismatch → 403), Rolle = Token-Snapshot (`principal.token_role`).
    **Kein** `workspace_member`-Lookup — ein gepinnter Token bleibt gueltig,
    bis er revoked wird (ADR-0023 Trade-off).
  - **JWT-Pfad**: `workspace_member`-Row pruefen (nicht-Mitglied → 403),
    Rolle = `WorkspaceRole(row)`.

### 2. `repositories/token_repository.py`

- `TokenAuthRow.role: WorkspaceRole`.
- `fetch_auth_by_hash` selektiert zusaetzlich `role`.
- `insert(..., role: WorkspaceRole)` schreibt die Snapshot-Rolle.

### 3. Service-Gates (require_role)

- `TokenService.create/list_all/revoke` → editor. `create`: `role =
  data.role or ctx.role`; explizit hoeher als Caller → 403 (Snapshot kann
  Caller-Rolle nicht uebersteigen).
- `Persona/Playbook/Resource Service.create/update` → editor.
- `PersonaPlaybookService.set_links`, `PlaybookResourceLinkService.set_links`
  → editor. (Listen/Get/list_links bleiben viewer = nur Membership.)
- `VersionStatusService._transition`: nach `validate_transition` das
  Rollen-Gate (`admin` fuer `to_status ∈ {active, inactive}`, sonst `editor`).
  Exponiert `required_role_for_transition(from, to)` fuer Test/Klarheit.

### 4. Test `apps/api/tests/test_rbac_matrix.py`

- Parametrisierte Matrix `{viewer, editor, admin} ×
  {create_persona, update_persona, transition_to_review,
  transition_to_active, delete_persona, list_members, create_invitation,
  create_token, list_dashboard}` → erwartetes Erlaubt/403 ueber `require_role`
  + `required_role_for_transition` (kein DB-Zwang, laeuft ueberall).
- Zusatz: DB-Integrationstests (skip ohne DB, Stil `test_tokens.py`) die die
  Gates am echten HTTP-Endpoint belegen (create_persona/transition/token),
  inkl. Token-Snapshot (Token erbt Ersteller-Rolle; editor kann kein
  admin-Token erzeugen).

`delete_persona`/`list_members`/`create_invitation` haben in dieser Stufe
keinen Endpoint (Prompt B); ihre Zeilen werden ueber `require_role` gegen die
Soll-Mindestrolle geprueft — die HTTP-Verdrahtung folgt in Prompt B.
