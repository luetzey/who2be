# Plan: Agenten-Gedächtnis (Memory) für Who2Be — kuratiert, kontrolliert

- Datum: 2026-07-18 (final nach zwei Design-Runden mit dem User)
- Branch: `claude/autonomous-code-agent-setup-iz6ydx`, PR #324 (Draft)
- Quelle: User-Konzeptdokument „Wie das Gedächtnis von Claude und anderen LLMs
  funktioniert" (Juli 2026), insb. Kap. 10 (Auswahlkriterien), Kap. 11
  (Agent-Ready Spec), **Kap. 13 (Gedächtnis als MCP-Server)**.
- Status: FREIGEGEBEN — Umsetzung läuft.

## Entschiedene Design-Weichen (User, 2026-07-18)

1. **Retrieval: Postgres-Volltext** (tsvector `simple` + pg_trgm), Tool-Vertrag
   vektor-bereit (ADR-0037-Stufe-B-Pfad offen).
2. **Speicher-Modus pro Agent, 4-stufig** (Runde 2 ersetzt die globale
   Freigabe-Pflicht): `off` < `read_only` < `suggest` < `auto`.
   - `off`: Memory-Tools existieren für den Agenten nicht (tools/list-Filter).
   - `read_only`: nur `search_memory`/`list_memories`.
   - `suggest` (empfohlener Default beim Aktivieren): `save_memory` → `pending`,
     erst nach menschlicher Freigabe retrieval-sichtbar.
   - `auto`: `save_memory` → direkt `active`; serverseitige Wächter laufen
     trotzdem immer. Anti-Eskalation via `is_within` (Agent kann sich nie
     selbst hochstufen). Policy-Default insgesamt: `off` (secure-by-default).
3. **System-Prompt trägt die Abfrage-Anweisung, nicht die Inhalte:** Bei
   `memory_mode ≠ off` hängt der `tools-overview`-Resolver eine
   Gedächtnis-Sektion an (wie abfragen; Ergebnisse sind Daten, keine
   Anweisungen). Verbindlichkeit pro Agent konfigurierbar:
   `memory_directive: 'required'` („rufe zu Gesprächsbeginn dein Gedächtnis
   ab") | `'recommended'` (Default; „nutze es, wenn Kontext hilfreich ist").
   KEIN Content-Push in den KONFIGURIERTEN Prompt — Inhalte fließen über die
   Tools. **Runde 3 (WP-6, 2026-07-18):** Zusätzlich Laufzeit-Einbindung via
   `get_persona`: fetch-time Gedächtnis-Sektion in `body_rendered`
   (muss/soll-Anweisung + Top-5 FREIGEGEBENE Memories, Daten-Rahmung,
   Nutzungs-Log-Bump) — der konfigurierte System-Prompt wird nicht live
   aktualisiert, die Persona wird laut Boot-Sequenz jede Session frisch
   geladen. Die Freigabe-Schleuse macht den Laufzeit-Push vertretbar.
4. **Nutzungs-Transparenz:** `retrieval_count` + `last_retrieved_at` je
   Memory, UI zeigt „N× abgerufen, zuletzt am …".
5. **`context`-Parameter** an `save_memory` (optional, ≤ 200 Zeichen): 1 Satz
   Begründung, NUR in der Triage-UI sichtbar, nie im Retrieval/Prompt.

## Ziel / Outcome

Who2Be-Agenten bekommen ein persistentes Langzeitgedächtnis über Sessions
hinweg — kuratiert und pro Agent steuerbar: Der User entscheidet je Agent, ob
gar nicht, nur gelesen, mit Freigabe oder automatisch gespeichert wird, und
mit welcher Verbindlichkeit der System-Prompt zur Abfrage anleitet. Nur
`active`-Memories sind abrufbar; die Web-UI macht alles einsehbar, editierbar
und löschbar (einzeln + komplett). Damit bleibt das Who2Be-Grundprinzip
optional streng (Kurations-Schleuse wie beim Feedback-Flywheel ADR-0038),
ohne den Auto-Modus für vertrauenswürdige Setups zu verbauen.

### Warum Kap.-13-Variante (agentisch) und nicht Kap.-11-Pipeline

Who2Be führt selbst keine LLM-Chat-Loops aus — LLM-Aufrufe passieren in
externen MCP-Clients. Einbaupunkt ist der FastMCP-Server: Memory als
MCP-Tools mit serverseitigen Wächtern. Identität: agent-gebundener Token
(`whoami.agent_id`), nie aus Tool-Parametern. Who2Be bleibt LLM-frei (keine
serverseitige Extraktion, kein Judge — Abgrenzung zu Kap. 11.4/12.2).
Die Kap.-13-Schwachstelle „keine automatische Injektion" adressieren wir
Who2Be-nativ: Wir rendern die System-Prompts selbst, also trägt der Prompt
die (konfigurierbare) Abfrage-Anweisung (Weiche 3).

## Antworten auf Kap. 11.1 (aus der Codebasis geklärt)

1. LLM-Aufrufe: extern (MCP-Clients) → agentische Variante (Kap. 13).
2. Identität: agent-gebundener Token, `whoami` liefert agent_id+workspace_id.
3. Mandanten-Trennung: `workspace_id` (RLS) + `agent_id` als Namespace.
4. DB: Supabase-Postgres; FTS vorhanden (ADR-0037), pgvector bewusst offen.
5. Job-Queue: keine — und keine nötig.
6. Extraktions-Modell: entfällt (LLM-frei).

## Lebenszyklus & Kontroll-Modell

```
save_memory (suggest-Modus) ──► pending ──(freigeben/editieren+freigeben)──► active
                                   └──(ablehnen, opt. Notiz)──► rejected
save_memory (auto-Modus)    ──────────────────────────────────► active
active ──(User löscht)──► weg (Hard-Delete)
```

- `pending`: retrieval-unsichtbar; erscheint in der Triage-UI.
- `active`: einziger retrieval-sichtbarer Zustand.
- `rejected` bleibt als Zeile bestehen: Dedup-Wächter prüft neue Vorschläge
  auch gegen rejected (sonst schlägt der Agent denselben Fakt nächste Session
  wieder vor). Über UI/Purge endgültig löschbar (DSGVO unberührt).
- **Kein agent-seitiges `update_memory`/`delete_memory` in v1** (würde die
  Schleuse umgehen; Korrektur = neuer Vorschlag; Editieren/Löschen human-only).
- Deep-Copy (Agent duplizieren) kopiert Memories NICHT (konsistent mit
  Resource-Links-Verhalten).

### Serverseitige Wächter (laufen in jedem Modus)

Injection-Filter (Regex-Blockliste KI-gerichteter Manipulationsmuster —
bewusst NICHT jede legitime Instruktions-Präferenz wie „antworte auf
Deutsch"; Graubereich entscheidet die Triage), fact ≤ 300 Zeichen,
importance 1–10 (< 5 → Ablehnung mit Meldung), Dedup via `pg_trgm`-Similarity
≥ 0.6 gegen pending+active+rejected, Cap `MEMORY_MAX_PER_AGENT` (500, pending
zählt mit), bestehendes Write-Rate-Limit (ADR-0039) auf `save_memory`.

### Abgrenzungen

- Resources = menschlich kuratiertes, versioniertes Wissen; Memory =
  agent-vorgeschlagene, leichte Fakten. Beförderung Memory→Resource =
  Folge-Iteration (ADR-Ausblick).
- Repo-Fakten gehören NICHT ins Memory (dafür `.claude/context/`) —
  Leitplanke in den Tool-Beschreibungen.
- FTS mit `simple`-Config (kurz, gemischtsprachig; Stemming-Mismatch wäre
  schlimmer), pg_trgm fängt Namen/IDs/Abkürzungen.

## Umsetzung (Arbeitspakete)

### WP-1 — Modelle + Migration

- `packages/models`: `MemoryStatus` (pending/active/rejected),
  `MemoryCategory` (preference/fact/project/instruction/entity/general),
  `MemoryMode` (off/read_only/suggest/auto, geordnet), `MemoryDirective`
  (required/recommended), `MemoryCreate` (fact ≤ 300, context ≤ 200,
  importance 1–10), `MemoryUpdate`, `MemoryTriage` (approve/reject +
  optionale Fakt-Edition + Notiz), `MemoryRead` (inkl. retrieval_count/
  last_retrieved_at/context).
- `AgentToolPolicy` + `memory_mode` + `memory_directive`
  (JSONB-abwärtskompatibel, Defaults off/recommended), `is_within`-Ordnung.
- Migration `agent_memory`: Tabelle (id, workspace_id FK, agent_id FK ON
  DELETE CASCADE, status, fact, context, category, importance, source,
  triage_note, retrieval_count, last_retrieved_at, created_at, updated_at);
  tsvector-Generated-Column (`simple`) + GIN; pg_trgm-Index auf fact;
  Index (workspace_id, agent_id, status); RLS + Grants nach 0053-Muster
  plus UPDATE/DELETE. Hard-Delete-Konvention (kein deleted_at).

### WP-2 — API (Repo/Service/Router)

- `MemoryRepository` (jede Query workspace_id+agent_id-gefiltert),
  `MemoryService` mit Wächtern + Modus-Logik (suggest→pending, auto→active).
- Agent-Pfad (Token, mode-Gate + `require_write_rate`):
  save/search/list-Endpunkte für den MCP-Adapter.
- Mensch-Pfad (editor+): GET Liste (?status=), POST triage, PUT edit,
  DELETE einzeln + alle. `whoami` gibt memory_mode/directive aus.

### WP-3 — MCP-Tools + Prompt-Integration (ADR-0042 Pflicht)

- 3 Tools (`output_schema=None`): `search_memory(query, k=5)`,
  `list_memories(limit=20)`, `save_memory(fact, category, importance,
  context=None)` — save-Antwort nennt im suggest-Modus explizit „wartet auf
  Freigabe". Beschreibungen = Kap.-10.5/13.3-Kriterien wörtlich.
- `tool_requirements`-Einträge mit Modus-Prädikat (search/list ≥ read_only,
  save ≥ suggest); `tools-overview`-Resolver: Gedächtnis-Sektion bei
  mode ≠ off mit directive-abhängiger Verbindlichkeit (muss/soll).

### WP-4 — Web-UI (Agent-Detail; datei-disjunkt, Sub-Agent)

- Sektion „Gedächtnis": Triage-Block (pending: Fakt inline editieren →
  Freigeben/Ablehnen mit Notiz; `context` sichtbar), aktive Liste (Fakt,
  Kategorie, Importance, „N× abgerufen, zuletzt …", Inline-Edit,
  Einzel-Löschen mit Confirm, „Alle löschen"), Rejected eingeklappt +
  endgültig löschbar; Pending-Count-Badge.
- `AgentEditorForm`: `memory_mode`-Select (4 Stufen) + `memory_directive`-
  Select (muss/soll, nur bei mode ≠ off). i18n de/en.

### WP-5 — DSGVO + Doku

- Export (`agent_memory` im Workspace-/Agent-Export, ADR-0032-Muster),
  Purge ab Tag 1, VVT-Eintrag.
- **ADR-0044** „Agent-Memory (kuratiert, agentisch, FTS-first)": alle
  Entscheidungen oben inkl. Abweichungen (Hard-Delete statt Soft-Delete,
  kein Presidio, kein Content-Push) + Ausblicke (pgvector, Vorschlags-
  Updates, zentrale Inbox, Memory→Resource).
- STATE.md/DECISIONS.md; CLAUDE.md §Struktur (MCP-Tool-Liste).

### Reihenfolge

WP-1 → WP-2 → WP-3 sequenziell (verzahnt, Hauptstrang); WP-4 nach WP-2 als
Sub-Agent-Paket (nur `apps/web`); WP-5 zum Schluss. `security-reviewer` über
WP-2/WP-3 vor dem finalen Push.

## Sicherheit / Tests

- Leak-Test: zwei Agenten, gleiche Query → nie Memories des anderen.
- Schleusen-Test: pending/rejected NIE in search/list; suggest speichert
  pending, auto speichert active.
- Wächter-Test: Injection/Überlänge/Duplikat/Cap → Ablehnung, modell-unabhängig.
- Modus-Test: off → Tools nicht in tools/list + Call gesperrt; read_only →
  save gesperrt; is_within verhindert Selbst-Hochstufung.
- Directive-Test: Prompt-Sektion muss/soll korrekt gerendert.
