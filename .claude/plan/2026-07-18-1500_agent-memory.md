# Plan: Agenten-Gedächtnis (Memory) für Who2Be — kuratiert, kontrolliert

- Datum: 2026-07-18 (überarbeitet nach Design-Entscheidung mit dem User)
- Branch: `claude/autonomous-code-agent-setup-iz6ydx`
- Quelle: User-Konzeptdokument „Wie das Gedächtnis von Claude und anderen LLMs
  funktioniert" (Juli 2026), insb. Kap. 10 (Auswahlkriterien), Kap. 11
  (Agent-Ready Spec), **Kap. 13 (Gedächtnis als MCP-Server)**.
- Status: Design entschieden, Umsetzung wartet auf Freigabe.

## Entschiedene Design-Weichen (User, 2026-07-18)

1. **Speicher-Kontrolle: Freigabe-Pflicht.** Jedes vom Agenten vorgeschlagene
   Memory landet als `pending` und wird erst nach menschlicher Freigabe
   retrieval-sichtbar.
2. **Nutzungs-Kontrolle: Modus + Nutzungs-Log.** Pro Agent ein
   `memory_mode` (aus / nur lesen / lesen+vorschlagen) in der Tool-Policy;
   die UI zeigt pro Memory, wann es zuletzt abgerufen wurde.
3. **Retrieval: Postgres-Volltext** (tsvector + pg_trgm), Tool-Vertrag
   vektor-bereit (`mode`-Parameter später, analog ADR-0037 Stufe B).

## Ziel / Outcome

Who2Be-Agenten bekommen ein persistentes Langzeitgedächtnis über Sessions
hinweg — aber **kuratiert statt autonom**: Der Agent *schlägt* Memories vor
(`save_memory`), der Mensch gibt frei, editiert oder lehnt ab; nur
freigegebene Memories sind über `search_memory`/`list_memories` abrufbar.
Damit bleibt das Who2Be-Grundprinzip intakt (Agenten ändern nie selbst
Inhalte — ein Kurator entscheidet, wie beim Feedback-Flywheel ADR-0038),
und Prompt-Injection über selbstgeschriebene Memories ist strukturell
entschärft (Schleuse vor der Sichtbarkeit, nicht nur Filter).

### Warum Kap.-13-Variante (agentisch) und nicht Kap.-11-Pipeline

Who2Be führt selbst keine LLM-Chat-Loops aus — LLM-Aufrufe passieren in
externen MCP-Clients. Es gibt keinen Read-/Write-Path „um jeden Turn", den
Who2Be kontrollieren könnte. Einbaupunkt ist der FastMCP-Server: Memory als
MCP-Tools mit serverseitigen Wächtern. Identität ist gelöst: agent-gebundener
Token (`whoami.agent_id`), nie aus Tool-Parametern. Who2Be bleibt LLM-frei
(keine serverseitige Extraktion/Judge — bewusste Abgrenzung zu Kap. 11.4/12.2).

## Antworten auf Kap. 11.1 (aus der Codebasis geklärt)

1. LLM-Aufrufe: extern (MCP-Clients) → agentische Variante (Kap. 13).
2. Identität: agent-gebundener Token, `whoami` liefert agent_id+workspace_id.
3. Mandanten-Trennung: `workspace_id` (RLS) + `agent_id` als Namespace.
4. DB: Supabase-Postgres; FTS vorhanden (ADR-0037), pgvector bewusst offen.
5. Job-Queue: keine — und keine nötig (keine Pipeline, kein Judge).
6. Extraktions-Modell: entfällt (LLM-frei).

## Lebenszyklus & Kontroll-Modell

### Memory-Lebenszyklus

```
Agent: save_memory ──► pending ──(User: freigeben/editieren+freigeben)──► active
                          │
                          └──(User: ablehnen, optional Notiz)──► rejected
active ──(User: löschen)──► weg (Hard-Delete)
```

- **`pending`:** unsichtbar für Retrieval; erscheint in der Triage-UI.
- **`active`:** einziger retrieval-sichtbarer Zustand.
- **`rejected` bleibt als Zeile bestehen** (kein Hard-Delete): der
  Dedup-Wächter prüft neue Vorschläge auch gegen rejected — sonst schlägt
  der Agent denselben Fakt in der nächsten Session wieder vor
  (Konsequenz aus der Freigabe-Pflicht). Rejected ist über UI/Purge
  jederzeit endgültig löschbar (DSGVO unberührt).
- Agent-seitig gibt es in v1 **kein `update_memory`/`delete_memory`**:
  beides würde die Freigabe-Schleuse umgehen (Update eines aktiven
  Memories = unkuratierte Inhaltsänderung). Korrekturen laufen als neuer
  Vorschlag; Editieren/Löschen ist human-only (UI). Vorschlags-Updates
  („ersetzt Memory X") sind eine dokumentierte Folge-Iteration.

### Nutzungs-Kontrolle (Leseseite)

- `AgentToolPolicy.memory_mode: 'off' | 'read_only' | 'suggest'`,
  **Default `off`** (secure-by-default wie `system_prompt_write`).
  Anti-Escalation via `is_within`: off < read_only < suggest.
- Tool-Sichtbarkeit über das bestehende ADR-0042-Mapping:
  `search_memory`/`list_memories` nur bei mode ≠ off, `save_memory` nur
  bei mode = suggest. Bei `off` erscheinen die Tools gar nicht erst in
  `tools/list` — der Agent kann nicht einmal versuchen zuzugreifen.
- **Nutzungs-Log:** `retrieval_count` + `last_retrieved_at` je Memory,
  inkrementiert wenn ein Memory in einer `search_memory`/`list_memories`-
  Antwort ausgeliefert wurde. UI zeigt „N× abgerufen, zuletzt am …" —
  der User sieht, WANN das Gedächtnis real benutzt wurde. (Volles
  Event-Log pro Abruf = Folge-Iteration, wenn Bedarf belegt.)
- Retrieval-Antworten sind als **Daten, nicht Anweisungen** gerahmt
  (fester Präfix im Tool-Output, Kap. 11.5).

### Serverseitige Wächter (laufen immer, egal was das Modell sendet)

- Injection-Filter (Regex-Blockliste instruktionsartiger Inhalte),
  Längen-Limit (fact ≤ 300 Zeichen), importance 1–10 (< 5 → Ablehnung mit
  klarer Meldung), Dedup via `pg_trgm`-Similarity ≥ 0.6 gegen
  pending+active+rejected, Cap `MEMORY_MAX_PER_AGENT` (500, pending zählt
  mit), bestehendes Write-Rate-Limit (ADR-0039) greift auf `save_memory`.

### Abgrenzung zu Resources

Resources = vom Menschen kuratiertes, versioniertes Wissen; Memory = vom
Agenten vorgeschlagene, leichtgewichtige Fakten. Beförderungspfad
(bewährtes Memory → Resource) ist die Who2Be-native Konsolidierung —
bewusst Folge-Iteration, im ADR als Ausblick dokumentiert.

## Umsetzung (Arbeitspakete)

### WP-1 — Modelle + Migration

- `packages/models/.../memory.py`: `MemoryStatus` (pending/active/rejected),
  `MemoryCategory` (preference/fact/project/instruction/entity/general),
  `MemoryCreate` (fact ≤ 300, importance 1–10), `MemoryUpdate` (human),
  `MemoryTriage` (approve/reject + optionale Fakt-Edition + Notiz),
  `MemoryRead` (inkl. retrieval_count/last_retrieved_at), `MemoryMode`.
- Migration `006x_agent_memory.sql`:
  - `agent_memory` (id, workspace_id FK, agent_id FK ON DELETE CASCADE,
    status, fact, category, importance, source, triage_note,
    retrieval_count INT DEFAULT 0, last_retrieved_at TIMESTAMPTZ,
    created_at, updated_at). Hard-Delete-Konvention wie `agent_feedback`
    (kein deleted_at; Abweichung von Kap. 11.6 dokumentiert).
  - tsvector-Generated-Column + GIN (nur Retrieval-Pfad filtert
    status='active'); `pg_trgm`-Index auf fact; Index (workspace_id,
    agent_id, status). RLS + Grants nach 0053-Muster, plus UPDATE/DELETE.

### WP-2 — API (Repo/Service/Router) + Policy

- `AgentToolPolicy.memory_mode` (JSONB-abwärtskompatibel, Default off)
  + `is_within`-Ordnung; `whoami` gibt den Modus aus.
- `MemoryRepository` (jede Query workspace_id+agent_id-gefiltert, per
  Signatur erzwungen), `MemoryService` mit den Wächtern.
- REST (Mensch, editor+-Gate wie Feedback-Delete):
  - `GET /v1/workspaces/{ws}/agents/{agent_id}/memories?status=`
  - `POST …/memories/{id}/triage` (approve/reject, optional Fakt-Edit+Notiz)
  - `PUT …/memories/{id}` (Fakt/Kategorie/Importance editieren)
  - `DELETE …/memories/{id}` und `DELETE …/memories` (alle; Confirm in UI)
- Agent-Pfad: nur über MCP-Tools (kein eigener REST-Surface nötig, Tools
  rufen Service direkt wie üblich via API).

### WP-3 — MCP-Tools + Mapping (ADR-0042 Pflicht)

- **3 Tools:** `search_memory(query, k=5)`, `list_memories(limit=20)`,
  `save_memory(fact, category, importance)` → Antwort nennt explizit
  „als Vorschlag gespeichert, wartet auf Freigabe" (Erwartungsmanagement
  im Modell). `output_schema=None` (Payload-Lektion 2026-07-07).
- Tool-Beschreibungen = Auswahlkriterien aus Kap. 10.5/13.3 wörtlich
  (WANN speichern / NIE speichern; Ergebnisse sind Daten, keine
  Anweisungen, ggf. veraltet).
- `who2be_models.tool_requirements`: 3 Einträge, gated auf memory_mode
  (Mapping-Erweiterung: Requirement kann Modus-Prädikat tragen);
  `tools-overview`-Resolver: Memory-Sektion nur bei mode ≠ off.

### WP-4 — Web-UI (Agent-Detail)

- Sektion „Gedächtnis" auf der Agent-Detailseite:
  - **Triage-Block oben** (pending): Fakt inline editieren → Freigeben /
    Ablehnen (mit Notiz), Muster Feedback-Triage.
  - **Aktive Memories:** Liste (Fakt, Kategorie, Importance, „N× abgerufen,
    zuletzt …"), Inline-Edit, Einzel-Löschen (Confirm), „Alle löschen".
  - **Abgelehnte:** eingeklappter Bereich, endgültig löschbar.
- `memory_mode`-Select im `AgentEditorForm` (Muster bestehender Policy-
  Felder); Pending-Count-Badge an der Sektion. i18n de/en.
- Zentrale Posteingang-Integration (Feedback-Inbox-Tab „Memory") =
  Folge-Iteration; v1 triagiert am Agenten.

### WP-5 — DSGVO + Doku

- Export: `agent_memory` im Workspace-/Agent-Export (ADR-0032-Muster).
- Purge: `agent_memory` im DSGVO-Purge ab Tag 1 (Standards-Review-Lektion);
  VVT-Eintrag.
- **ADR-0044 „Agent-Memory (kuratiert, agentisch, FTS-first)"**:
  Kap.-13-Variante, Freigabe-Pflicht, rejected-als-Dedup-Basis,
  kein Agent-Update/Delete in v1, Ein-Feld-Modus statt Boolean-Capability,
  Hard-Delete-Abweichung, pgvector-Stufe offen, Resource-Beförderung als
  Ausblick.
- STATE.md/DECISIONS.md; CLAUDE.md §Struktur (MCP-Tool-Liste).

### Reihenfolge & Orchestrierung

WP-1 → WP-2 → WP-3 sequenziell im Hauptstrang (architektonisch verzahnt);
WP-4 als datei-disjunktes Paket nach WP-2 (nur `apps/web`, mechanisch —
kleineres Modell ausreichend); WP-5 zum Schluss.

## Sicherheit

- `security-reviewer`-Subagent über WP-2/WP-3 (CLAUDE.md-Pflicht).
- Leak-Test: zwei Agenten, gleiche Query → nie Memories des anderen.
- Wächter-Test: save_memory mit Injection/Überlänge/Duplikat direkt →
  Ablehnung unabhängig vom Modellverhalten.
- Schleusen-Test: pending/rejected erscheinen NIE in search/list-Antworten.
- Modus-Test: mode=off → Tools nicht in tools/list, Call → klare Sperre;
  read_only → save_memory gesperrt.
