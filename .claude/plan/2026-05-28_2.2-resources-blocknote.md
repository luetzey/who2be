## Antwort auf die Frage: Phasen & Stand

| Phase | Inhalt | Stand |
|---|---|---|

Das Repo ist auf 2.2 vorbereitet: `EntityType` enthält bereits `'resource'`, `version_status.py` kennt das `"resource"`-Label, die Dashboard-Activity-Query hat den Resource-Zweig. Migrationen enden bei `0014`, ADRs bei `0020`.

## Context

2.2 fügt **Resources** als zweite Wissensebene hinzu: versionierte Dokumente mit Notion-artigem Block-Editor. Playbooks können auf **einzelne Blöcke** einer Resource verweisen (Block-Refs, immer auf `latest active`). Agenten ziehen Resource-Blöcke über neue MCP-Tools.

**Entscheidung (vom User bestätigt):** Statt des im Master-Plan vorgesehenen TipTap-Eigenbaus nutzen wir **BlockNote** (`@blocknote/core` + `@blocknote/react` + `@blocknote/mantine`). Begründung: Slash-Menü, Drag-Handle, Block-IDs und Block-Typen kommen out-of-the-box; **stabile Block-IDs sind nativ** (jeder Block hat `id`) → die geplante eigene `BlockId`-Extension entfällt. Umfang dieser Session: **komplett 2.2a (Backend) + 2.2b (Frontend) + MCP**, gepusht auf `claude/phase-2-app-plan-2.2-xehmr`. Kein PR ohne explizite Aufforderung.

**Editor-Isolation:** BlockNote wird als gekapselte Insel mit `@blocknote/mantine` eingebunden (eigener Style-Scope, lokale Inter-Schrift → kein CDN/CSP-Problem). Der `@blocknote/shadcn`-Pfad scheidet aus, weil er Portals in unseren geteilten `DropdownMenu/Popover/Select`-Primitives deaktivieren müsste. Der Editor ist damit eine dokumentierte Ausnahme vom Token-System (analog wie der Master-Plan TipTap-Content als a11y-Sonderfall behandelt).

## Phase 2.2a — Backend

### Models (`packages/models/src/who2be_models/`)
Neue Datei `resource.py` (Vorlage `playbook.py`):
- `ResourceBlock(BaseModel, extra="allow")`: `id: str (1–100)`, `type: str (1–50)` — BlockNote-Block, weitere Felder offen.
- `ResourceContent(extra="forbid")`: `description: str = "" (max 2_000)`, `blocks: list[ResourceBlock] (max_length=2_000)`; **`model_validator`** der die JSON-Serialisierung auf < 1 MB begrenzt (F-01-DoS-Linie, da Blocks `extra="allow"` sind).
- `ResourceCreate` / `ResourceUpdate` / `ResourceRead` / `ResourceVersionRead` — exakt analog Playbook (mit `current_status`, `has_pending_draft`, `status`). `ResourceRead` ohne denormalisierte Filterspalten (Resources haben keine Tags im MVP).
- `ResourceLinkRead`: `resource_id, resource_name, block_id, position, available: bool, preview: str | None`.
- `ResourceLinkSet(extra="forbid")`: `links: list[ResourceLinkItem] (max_length=200)`, `ResourceLinkItem` = `{resource_id: UUID, block_id: str (1–100), position: int (ge=0)}`.
- In `__init__.py` exportieren (Liste + `__all__`).

### Migrationen (`apps/api/src/who2be_api/migrations/`)
- **`0015_resource.sql`** (Vorlage 0002/0003 + 0011): `resource(id, workspace_id NOT NULL, owner_id NOT NULL, name, current_version DEFAULT 1, created_at, updated_at)`, `UNIQUE (workspace_id, id)` (FK-Ziel). `resource_version(resource_id, version, content jsonb, status text DEFAULT 'inactive' CHECK(...), created_by, created_at, PK(resource_id, version))`. Drei **Partial-Unique-Indizes** `WHERE status IN ('active'|'draft'|'review')` (Invariante wie 0011).
- **`0016_playbook_resource_link.sql`** (Vorlage 0004 + 0014): `playbook_resource_link(workspace_id NOT NULL, playbook_id, resource_id, block_id text NOT NULL, position smallint NOT NULL DEFAULT 0, owner_id, created_at, PK(playbook_id, resource_id, block_id))`. Composite-FKs `(workspace_id, playbook_id)→playbook` und `(workspace_id, resource_id)→resource` `ON DELETE CASCADE` (Defense-in-Depth). Index auf `(workspace_id, resource_id)`.
- Idempotenz-/Migrations-Test in `apps/api/tests/test_migrations.py` ergänzen.

### Repository / Service / Router
- `repositories/resource_repository.py` — Copy-&-adapt von `playbook_repository.py` (`_SELECT_CURRENT`/`_SELECT_ACTIVE`, `insert/list_by_workspace/fetch/update/list_versions/fetch_version`, `ResourceUpdateOutcome` mit `draft_exists`-Konflikt, FOR-UPDATE-Draft-on-Edit). Ohne Tag/Trigger-Filter.
- `services/resource_service.py` — Copy von `playbook_service.py` (404/409-Mapping, `active_only=ctx.is_api_token`).
- `services/playbook_resource_link_service.py` + `repositories/playbook_resource_link_repository.py` — Vorlage `persona_playbook_*`. `set_links` (atomar, FOR UPDATE auf Playbook, Validierung dass alle `resource_id` im Workspace) + `list_links`. `list_links` joint auf die **aktive** Resource-Version, prüft pro Link ob `block_id` in `content.blocks` existiert (`available`), extrahiert `preview` (erste 200 Zeichen Plain-Text des Blocks via Helper `block_plain_text(block)` — rekursives Einsammeln der `text`-Felder).
- `routers/resources.py` — Copy von `playbooks.py`: `GET/POST /resources`, `GET/PUT /resources/{id}`, `GET /resources/{id}/versions`, `GET .../versions/{v}`, `POST .../versions/{v}/transition` (nutzt `VersionStatusService`). **Transition für Resource:** `version_status.py` um `transition_resource_version` + `_RESOURCE_TABLES = ("resource","resource_version","resource_id")` erweitern (zwei kleine Methoden, identisches `_transition`).
- `routers/playbook_resources.py` (Prefix `/playbooks`, eigene Datei wie `persona_playbooks.py`): `GET /playbooks/{id}/resource_links`, `PUT /playbooks/{id}/resource_links`.
- In `main.py`: `resources` und `playbook_resources` Router unter `_WORKSPACE_PREFIX` einhängen.

### Dashboard
- Resource-Status in KPIs/Distribution/Activity aufnehmen: `dashboard_repository.py` + `dashboard.py`-Modelle um `resource`-Distribution erweitern; Activity-Query bezieht Resource bereits konzeptionell mit ein (Zweig finalisieren).

### MCP (`apps/mcp/src/who2be_mcp/`)
- `client.py`: Methoden `list_resources()`, `get_resource(resource_id)`, `get_playbook_resource_links(playbook_id)`.
- `server.py`: Tools
  - `list_resources()` → Active-Resources mit `id, name, block_count`.
  - `fetch_resource(resource_id, block_ids?)` → ganze Active-Version oder gefilterte Blöcke (Filter clientseitig im Tool über `content.blocks`).
  - `fetch_playbook` erweitern: gibt `PlaybookWithResources` zurück (neues lokales Modell wie `PersonaWithPlaybooks`) = Playbook + `linked_blocks: list[ResourceLinkRead]`. Kein Auto-Inline; nur Pointer + Preview.

### Tests (Backend)
- `apps/api/tests/test_resources.py` — CRUD, Versionierung, Draft-on-Edit-409, Status-Transition erlaubt/verboten, Invariante „max. 1 active" (Doppel-Insert). Vorlage `test_playbooks.py`.
- `apps/api/tests/test_playbook_resources.py` — Link-Set-Replace atomar, `available=false` wenn Block in neuer Active-Version fehlt, Cross-Workspace-Link → Fehler.
- MCP-Tests (`apps/mcp/tests/`) — `fetch_resource` mit/ohne `block_ids`, `fetch_playbook.linked_blocks`.

## Cross-cutting

- **Security** (`security-reviewer`-Subagent über den Diff laufen lassen): jede Query `WHERE workspace_id = $1`; Composite-FKs verhindern Cross-Workspace-Links; Block-Preview server-seitig auf 200 Zeichen + Plain-Text begrenzt (kein HTML-Leak); BlockNote rendert via React (kein `dangerouslySetInnerHTML`) → kein XSS-Vektor; Content-Größe per `model_validator` gedeckelt.
- **CSP/Caddy** (`deploy/hetzner/Caddyfile`): BlockNote-Insel lädt lokale Fonts/CSS (gebündelt) → i. d. R. keine Änderung. Falls Build externe Assets zieht: web-CSP minimal erweitern; **bewusst keine** Header in `apps/web/nginx.conf`.
- **Logging**: keine neue Achse nötig (`workspace_id` ist seit 2.1 im Context).
- **Pagination**: `core/pagination.py` Keyset-Codec für Resources wiederverwenden.
