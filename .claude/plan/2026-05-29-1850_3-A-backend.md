## Scope

### 1. Section-aware Block-Refs (F-12)

Neuer Helper `block_section_text(blocks, anchor_block_id) -> (ids, text)` in
`playbook_resource_link_repository.py`:

- Findet den Anker (`block.id == anchor_block_id`).
- Wenn Anker nicht gefunden → `([], "")`.
- Wenn Anker kein Heading (`type != "heading"`) → wir loggen nicht, geben
  aber `([anchor_id], plain_text_of(anchor))` zurueck, damit die Lese-Schicht
  fuer Bestandsdaten nicht crasht. **Validierung gegen Heading-Pflicht
  passiert im Service**, nicht im Repo — Service kennt 422.
- Anker ist Heading: sammelt alle Bloecke ab Anker bis exklusive naechstem
  Heading mit `props.level == anchor.props.level`. Default-Level = `1`,
  wenn `props.level` fehlt (BlockNote-Default fuer h1).
- Liefert `(section_block_ids: list[str], section_text: str)` —
  `section_text` ist Klartext aller Section-Bloecke joined mit `"\n\n"`,
  abgeschnitten auf 400 Zeichen.

Felder auf `ResourceLinkRead` (in `packages/models/src/who2be_models/resource.py`):

- `section_block_ids: list[str] = Field(default_factory=list)` — Block-IDs
  der gesammelten Section (inkl. Anker; leer wenn Anker nicht in Active und
  nicht in Current).
- `section_preview: str | None = None` — bis zu 400 Zeichen Klartext.
- `available_in: Literal["active", "draft"] | None = None` — wo der Anker
  aufgeloest werden konnte (siehe Step 2).

Felder `available` (bool) und `preview` (str|None) bleiben aus
Wire-Backward-Compat (Frontend Track B/C ist noch nicht umgestellt).
`available` = `available_in is not None`. `preview` bleibt der bisherige
Single-Block-Preview-Text (200 Zeichen) — die neuen Felder geben die
Section-Sicht zusaetzlich raus.

`_to_link_read` baut beide Sichten aus demselben Quell-Block-Array. Wenn
`section_preview` knapp 400 Zeichen ist, ist `preview` (200 chars) ein
Truncate des ersten Blocks — bleibt also unveraendert zu vorher.

**Service-Validation** in `PlaybookResourceLinkService.set_links`:

- Vor der Repo-Schreibung: zu jedem `item` die zugeordnete Active-Version
  der Resource laden (oder Current, wenn keine Active). Wenn der Block
  in der gefundenen Version existiert und kein `type == "heading"` ist,
  422 mit Microcopy `"Nur Heading-Bloecke sind als Anker erlaubt."`.
- Wenn der Block nicht (mehr) existiert: nicht ablehnen — Set bleibt
  bewahrenswert, der Read meldet `available_in=None`, das Frontend zeigt
  "Block geloescht". Begruendung: ein Heading kann nach Edit-Discard
  rueckverfuegbar werden.
- Helper `_load_resource_blocks(workspace_id, resource_ids)` im Repo:
  liefert pro Resource-ID die Blocks der **Active oder Current** Version
  (siehe Step 2). Service nutzt das.

### 2. Available-Fallback (F-10)

`list_links` joint zusaetzlich auf `current_version`:

```sql
SELECT
  prl.resource_id, prl.block_id, prl.position,
  r.name AS resource_name,
  rva.content AS active_content,
  rvc.content AS current_content,
  CASE WHEN rva.resource_id IS NOT NULL THEN 'active'
       WHEN rvc.resource_id IS NOT NULL THEN 'draft'
  END AS available_in_hint
FROM playbook_resource_link prl
JOIN resource r ON r.id = prl.resource_id
LEFT JOIN resource_version rva
       ON rva.resource_id = r.id AND rva.status = 'active'
LEFT JOIN resource_version rvc
       ON rvc.resource_id = r.id AND rvc.version = r.current_version
WHERE prl.playbook_id = $1 AND prl.workspace_id = $2
ORDER BY prl.position, prl.resource_id, prl.block_id
```

Hinweis: der `available_in_hint`-Spaltenwert ist ein Fallback fuer den
Resource-Stand insgesamt; **pro Block** gilt: bevorzugt Active, sonst
Current. Im `_to_link_read` resolven wir den Block in der Reihenfolge
(`active_content`, `current_content`) und setzen `available_in` auf
`"active"` / `"draft"` / `None`. Das hint-Feld brauchen wir also nicht
extra mitzunehmen — der Match-Pfad reicht.

`current_content` kann gleich `active_content` sein, wenn die Active-
Version auch die Current-Version ist; dann liefert der Block-Match
trotzdem `available_in='active'`, weil wir Active zuerst pruefen. (Wenn
Active und Current verschiedene Versionen sind und beide den Block haben,
gewinnt Active.)

### 3. Reverse-Lookups (F-11, F-16)

Neuer Router `routers/usages.py` (registriert mit `_WORKSPACE_PREFIX`).
Zwei Endpoints:

- `GET /playbooks/{playbook_id}/usages` → `list[PlaybookUsage]` —
  Quelle: `persona_playbook` JOIN `persona`.
  - Workspace-Check: Playbook muss zum Workspace gehoeren, sonst 404.
  - Cross-Workspace: `persona_playbook` ist via Composite-FKs auf den
    gleichen Workspace gepinnt; wir filtern trotzdem explizit auf
    `pp.workspace_id = $ws` (Defense).
- `GET /resources/{resource_id}/usages` → `list[ResourceUsage]` —
  Quelle: `playbook_resource_link` GROUP BY `playbook_id`, COUNT(*).
  - Workspace-Check analog.

Neues Repository-File `repositories/usage_repository.py`
(`PgUsageRepository` mit zwei Methoden) und Service
`services/usage_service.py` mit Workspace-Validation +
Not-Found-Handling.

Sortierung: `persona.name ASC` / `playbook.name ASC` — stabil und
nuetzlich fuer die UI-Liste.

### 4. Tags-DISTINCT-Endpoint (F-08)

`GET /v1/workspaces/{ws}/playbooks/tags` → `list[str]` (sortiert).

Implementation:

```sql
SELECT DISTINCT tag
FROM playbook, unnest(tags) AS tag
WHERE workspace_id = $1
ORDER BY tag ASC
```

Im `PgPlaybookRepository` als `list_distinct_tags(workspace_id)`.
Service-Methode `PlaybookService.list_tags(ctx)` — kein Role-Gate
(Lesen), Workspace-Membership reicht.

Router-Route in `routers/playbooks.py` **vor** `/{playbook_id}`
einsortieren (UUID-Validation wuerde `tags` sonst als 422 ablehnen,
bevor die Konstante-Route greift).
