# Plan: MS-2 C4 — CI/CD-Pipeline (GHCR-Build + SSH-Deploy)

## Context

Roadmap (`.claude/plan/2026-05-24_who2be-mvp-roadmap.md` §MS-2 C4):

> `.github/workflows/deploy.yml` baut die drei Images auf
> `ghcr.io/luetzey/who2be-*` und triggert per SSH `docker compose pull && up -d`
> auf dem Hetzner-Host. Trigger: push auf `main` nach gruener CI.

C2 (Supabase-Compose, PR #14) und C3 (App-Compose, PR #13) sind in `main`.
Beide tragen `image:`-Tags der Form `ghcr.io/luetzey/who2be-{api,web,mcp}:
${IMAGE_TAG:-latest}`. C4 muss diese Tags mit echten Artefakten fuellen
und den Pull-and-Restart auf dem Host triggern.

## Approach (Designentscheidungen)

### 1. Eigener Workflow `deploy.yml`, **nicht** Erweiterung von `ci.yml`

Begruendung: `ci.yml` triggert auf PR + Push-main, deckt Lint/Type/Test ab.
Deploy ist ausschliesslich `push: main` + `workflow_dispatch` (manueller
Rerun). Trennung haelt CI-Latenz auf PRs niedrig und macht den Deploy-Flow
in der Actions-UI sichtbar getrennt.

### 2. Trigger-Bedingungen

- `on: push: branches: [main]` — automatischer Build+Push+Deploy.
- `on: workflow_dispatch:` — Operator kann manuell einen Rerun anstossen
  (z. B. wenn der Host kurz down war).
- **Kein `workflow_run`-Coupling an `ci.yml`** — der Push-on-main-Pfad
  bekommt die CI-Pruefung bereits via Branch-Protection-Rule (PR-Merge
  voraussetzt gruenen `ci.yml`-Run); der Deploy laeuft unabhaengig
  weiter, falls jemand direkt nach main pusht.

### 3. Job 1 `build-and-push` — Matrix ueber drei Images

`strategy.matrix.image: [api, web, mcp]` mit `dockerfile` und ggf.
`build-args` pro Eintrag. Ein parallel laufender `docker/build-push-action`
ist pro Image massentauglich und gut cacheable (`type=gha`).

- **Tags pro Image**: `ghcr.io/luetzey/who2be-${image}:${{ github.sha }}`
  und `ghcr.io/luetzey/who2be-${image}:latest`. SHA-Tag ist
  unveraenderbar (gut fuer Rollback), `latest` zeigt auf den letzten
  gruenen Build (Bequemlichkeit fuer manuelle `docker compose pull`).
- **GHCR-Login**: `GITHUB_TOKEN` reicht — kein Personal Access Token noetig.
- **Permissions** im Workflow: `packages: write`, `contents: read`.
- **Web-Build-Args**: `VITE_API_BASE_URL`, `VITE_SUPABASE_URL`,
  `VITE_SUPABASE_ANON_KEY` als **Repository Variables** (non-secret —
  Domain/Anon-Key sind oeffentlich). Werden nur dem Web-Matrix-Eintrag
  als `build-args` mitgegeben.

### 4. Job 2 `deploy` — SSH zum Hetzner-Host (optional, hinter Secret-Gate)

`needs: build-and-push`. `if: vars.DEPLOY_HOST != ''` — solange der
Operator die Deploy-Variables nicht gesetzt hat, ueberspringt der
Job sauber, ohne den Workflow rot zu faerben. Damit ist der Build+Push
schon vor dem Server-Bring-up nutzbar.

Wenn die Variables/Secrets gesetzt sind:
- **Vars (non-secret)**: `DEPLOY_HOST`, `DEPLOY_USER`,
  `DEPLOY_PROJECT_DIR` (Default `/opt/who2be`).
- **Secrets**: `DEPLOY_SSH_KEY` (Private-Key, ED25519 empfohlen),
  optional `DEPLOY_SSH_KNOWN_HOSTS` (Public-Key des Hosts).
- **Schritt**: `webfactory/ssh-agent` fuer den Key, `ssh-keyscan` fuer
  Known-Hosts (falls Variable leer ist), dann `ssh ${USER}@${HOST}
  '/opt/who2be/deploy/hetzner/scripts/deploy.sh <sha>'`.
- Das eigentliche Deploy-Skript liegt **auf dem Server** (im
  ausgecheckten Repo); CI ruft nur an. Vorteil: kein in-line bash im
  workflow.yml, das Skript ist im Repo reviewbar.

### 5. Helper-Skript `deploy/hetzner/scripts/deploy.sh`

Einfacher Bash-Wrapper (POSIX, `set -euo pipefail`):
1. Argumentpruefung: ein Commit-SHA.
2. `cd ${PROJECT_DIR:-/opt/who2be}`.
3. `git fetch origin main && git checkout ${sha}` — sorgt dafuer, dass
   die `.env`-Pfade und Compose-Files zum Image-Stand passen.
4. Update der Image-Tags in `deploy/hetzner/.env` (sed in-place):
   `API_IMAGE_TAG=${sha}`, `WEB_IMAGE_TAG=${sha}`, `MCP_IMAGE_TAG=${sha}`.
5. `docker compose -f deploy/hetzner/who2be/docker-compose.yml
   --env-file deploy/hetzner/.env pull api web migrate`
   (mcp wird nur on-demand gepullt, da Profil-only).
6. `docker compose ... up -d --wait`.
7. Smoke: `curl -fsS http://localhost:8000/v1/health` via
   `docker compose ... exec api ...` (oder direkt
   `curl https://api.<DOMAIN>/v1/health`).
8. Log-Tail bei Fehler.

Auf dem Server muss der Deploy-User in der `docker`-Gruppe sein und
auf das Project-Dir Schreibrechte haben — Voraussetzung wird in C1
dokumentiert; in `deploy/hetzner/README.md` notieren wir es bereits.

### 6. Caveat: Web-Image ist Multi-Tenant-spezifisch

Die `VITE_*`-Werte sind beim Build in das Bundle gebrannt. Mit der
gewaehlten Variant (Repository Variables) gehoert das Image jeweils
**zu einem konkreten Domain-Tupel**. Das ist fuer MVP OK (eine Hetzner-
Instanz). Wenn spaeter Staging/Prod beide aus demselben Repo deployen
sollen, wird das Web-Build matrix-erweitert oder als Image-Variant
gespeichert — eigene Folge-Task, vermerken in `Out of Scope`.

## File-by-file Changes

### A. `.github/workflows/deploy.yml` — NEU

Aufbau (Pseudostruktur):

```yaml
name: Deploy
on:
  push: { branches: [main] }
  workflow_dispatch:
permissions:
  contents: read
  packages: write
jobs:
  build-and-push:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        include:
          - image: api
            dockerfile: apps/api/Dockerfile
          - image: web
            dockerfile: apps/web/Dockerfile
            build_args: |
              VITE_API_BASE_URL=${{ vars.VITE_API_BASE_URL }}
              VITE_SUPABASE_URL=${{ vars.VITE_SUPABASE_URL }}
              VITE_SUPABASE_ANON_KEY=${{ vars.VITE_SUPABASE_ANON_KEY }}
          - image: mcp
            dockerfile: apps/mcp/Dockerfile
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/metadata-action@v5
        id: meta
        with:
          images: ghcr.io/luetzey/who2be-${{ matrix.image }}
          tags: |
            type=raw,value=latest
            type=sha,format=long
      - uses: docker/build-push-action@v6
        with:
          context: .
          file: ${{ matrix.dockerfile }}
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha,scope=${{ matrix.image }}
          cache-to: type=gha,mode=max,scope=${{ matrix.image }}
          build-args: ${{ matrix.build_args }}

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    if: vars.DEPLOY_HOST != ''
    steps:
      - uses: webfactory/ssh-agent@v0.9.0
        with:
          ssh-private-key: ${{ secrets.DEPLOY_SSH_KEY }}
      - name: Trust host
        run: |
          mkdir -p ~/.ssh
          if [ -n "${{ vars.DEPLOY_SSH_KNOWN_HOSTS }}" ]; then
            echo "${{ vars.DEPLOY_SSH_KNOWN_HOSTS }}" > ~/.ssh/known_hosts
          else
            ssh-keyscan -H "${{ vars.DEPLOY_HOST }}" >> ~/.ssh/known_hosts
          fi
      - name: Deploy
        run: |
          ssh "${{ vars.DEPLOY_USER }}@${{ vars.DEPLOY_HOST }}" \
              "${{ vars.DEPLOY_PROJECT_DIR }}/deploy/hetzner/scripts/deploy.sh" \
              "${{ github.sha }}"
```

### B. `deploy/hetzner/scripts/deploy.sh` — NEU

```bash
#!/usr/bin/env bash
# Wird vom CI/CD-Workflow (siehe .github/workflows/deploy.yml) via SSH
# aufgerufen. Argument: ein Commit-SHA, dessen Images bereits auf GHCR
# liegen. Wechselt im Repo-Klon auf diesen SHA, setzt die Image-Tags
# in der .env, pullt und faehrt den Stack hoch.
set -euo pipefail
SHA="${1:?Usage: deploy.sh <commit-sha>}"
PROJECT_DIR="${PROJECT_DIR:-/opt/who2be}"
cd "$PROJECT_DIR"
git fetch origin main
git checkout "$SHA"
ENV_FILE="deploy/hetzner/.env"
COMPOSE="docker compose -f deploy/hetzner/who2be/docker-compose.yml --env-file $ENV_FILE"
# Idempotente Tag-Updates in der .env (kein Append, sondern Replace).
for var in API_IMAGE_TAG WEB_IMAGE_TAG MCP_IMAGE_TAG; do
    if grep -q "^${var}=" "$ENV_FILE"; then
        sed -i "s|^${var}=.*|${var}=${SHA}|" "$ENV_FILE"
    else
        echo "${var}=${SHA}" >> "$ENV_FILE"
    fi
done
$COMPOSE pull api web migrate
$COMPOSE up -d --wait --remove-orphans
$COMPOSE ps
```

Permissions auf dem Server: `chmod +x` ist in C1 zu setzen oder per
Repo-Default `executable bit` (lass die Datei mit `chmod +x` im Repo
committen — funktioniert auch unter Linux beim Checkout).

### C. `deploy/hetzner/README.md` — Ergaenzung

Sektion **"CI/CD (MS-2 C4)"** mit:
- Workflow-Pfad + Trigger.
- Liste der Repository-Variables (`VITE_*`, `DEPLOY_HOST`,
  `DEPLOY_USER`, `DEPLOY_PROJECT_DIR`, `DEPLOY_SSH_KNOWN_HOSTS`).
- Liste der Repository-Secrets (`DEPLOY_SSH_KEY`).
- Hinweis: `deploy`-Job ueberspringt sich sauber, solange `DEPLOY_HOST`
  nicht gesetzt ist — Build-Pipeline laeuft bereits.

## Wiederverwendung

- Bestehender `ci.yml`-Workflow bleibt unveraendert; deploy.yml haengt
  sich semantisch hintenan, ist aber technisch unabhaengig.
- Image-Tag-Strategie (`API_IMAGE_TAG`, `WEB_IMAGE_TAG`, `MCP_IMAGE_TAG`)
  ist bereits in C3's `who2be/docker-compose.yml` verkabelt — wir
  uebernehmen sie nur.
- `deploy/hetzner/README.md`-Stil + Querverweise wie in C3.

## Verifikation

1. **Workflow-Syntax** statisch (kein laufender CI noetig):
   ```bash
   uvx --from yamllint yamllint -d '{extends: default, rules: {line-length: disable, document-start: disable, comments: {min-spaces-from-content: 1}}}' .github/workflows/deploy.yml
   ```
   (Optional `actionlint`, falls im Pfad.)
2. **Skript-Syntax**: `bash -n deploy/hetzner/scripts/deploy.sh`.
3. **Shellcheck**: `shellcheck deploy/hetzner/scripts/deploy.sh`.
4. **Compose-Configs unbeeintraechtigt** — `docker compose config` auf
   beide Stacks.
5. **Python+Web-Suite** unbeeintraechtigt.
6. **Live-Test des Build-Jobs** passiert erst beim Merge auf `main` — im
   PR-Body ausdruecklich als Akzeptanzkriterium markiert.

## Out of Scope (bewusst)

- C1 Server-Provisioning (`docker`-Group, SSH-Hardening, deploy-User).
- C5 Backup-Skript + RUNBOOK.
- C6 E2E-Smoke gegen die produktive Instanz.
- Staging-/Multi-Env-Web-Build (siehe Approach §6).
- Rollback-Workflow per Commit-SHA — manuell per `*_IMAGE_TAG=<sha>` in
  der `.env` + `up -d --wait`; eigener Workflow waere overkill.
- Image-Scanning / `pip-audit` / `npm audit` als Pflicht-Step — eigene
  Hardening-Task (Backlog).
- Build-Cache-Eviction, Image-Retention auf GHCR — Default reicht fuer MVP.
